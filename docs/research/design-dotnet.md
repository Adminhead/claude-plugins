# C#/.NET plugins and `dotnet-meta`: design

Status: draft for review, 2026-10-17. Design only; nothing in `plugins/` is created yet.

The user asked for C#/.NET skills and plugins with a `dotnet-meta`. This reverses the adoption plan's "Not adopted: vendor-specific sets (... .NET ...)" row for .NET only; that row needs an edit when this lands.

Sources surveyed: the official [dotnet/skills](https://github.com/dotnet/skills) (cloned to `3rd-party/dotnet-skills`, overview in `docs/3rd-party/dotnet-skills/`), [microsoft/skills](https://github.com/microsoft/skills) (cloned to `3rd-party/microsoft-skills`), and the .NET material in awesome-copilot, claude-skills, ECC and wshobson-agents.

## Summary

- **Port from dotnet/skills, don't cross-depend on it.** It is the best .NET source by a wide margin (MIT, the .NET team, eval-backed, updated daily), but its marketplace packs up to 24 skills and 10 Copilot-format agents per plugin, with 400 to 1,000-character "ALWAYS USE" descriptions. Allowlisting it would expose all 16 plugins and a router skill that tells the model to install more of them.
- **13 focused skill plugins** (4 in `dotnet-meta`, 9 direct installs) plus 6 optional ones, each merging several upstream skills into one SKILL.md plus references. Upstream has 105 skills; the ports keep about 70 of them as reference files and skip the rest.
- **Other sources fill gaps only.** awesome-copilot contributes two new plugins (`roslyn-analyzers`, `aspire`), two optional ones (`xaml-mvvm`, `winui`) and deltas (System.CommandLine v2, async and cancellation rules); wshobson contributes a Dapper reference. claude-skills, ECC and microsoft/skills (Azure SDK only) contribute nothing.
- **`dotnet-meta`** = `programming-core`, `csharp`, `msbuild`, `dotnet-testing`, `nuget`, `omnisharp@claude-code-lsps`. Four new listing entries, at most ~1,400 characters, against ~30,000 characters for the upstream plugins that cover the same ground (`dotnet`, `dotnet-msbuild`, `dotnet-test`, `dotnet-nuget`).
- ASP.NET Core, EF Core, Blazor, MAUI, Aspire, Roslyn analyzers, upgrades, diagnostics and performance stay direct installs.
- **LSP is the weak spot.** `omnisharp@claude-code-lsps` (boostvolt) runs `OmniSharp -lsp`, and its SessionStart hook runs `brew install omnisharp-mono` when brew exists. OmniSharp is the legacy server; Microsoft's current one is `roslyn-language-server`, which upstream's `dotnet` plugin launches with `dnx --prerelease`. See open question 1.

### Cross-dependency on `dotnet-agent-skills`: rejected

dotnet/skills does ship `.claude-plugin/marketplace.json` (name `dotnet-agent-skills`). Weighing it as a cross-marketplace dependency:

| For | Against |
|---|---|
| Maintained by the .NET team, updated daily, regression-tested by evals; ports go stale and must be re-diffed | Granularity: `dotnet-test` is 24 skills + 10 agents (~14,200 description chars, ~3,500 tokens of listing every turn); `dotnet-msbuild` is 19 skills + 3 agents + an unpinned prerelease MCP server (~12,100 chars). A dependency installs the whole plugin |
| Small plugins exist: `dotnet-data` (2 skills), `dotnet-aspnetcore` (2), `dotnet-nuget` (1), `dotnet-winforms` (1), `dotnet-ai` (1) | Descriptions are tuned for their harness ("ALWAYS USE before running .NET tests", "MANDATORY", "MUST USE") and would outcompete our skills; `dotnet-test`'s polyglot skills (`code-testing`, `test-anti-patterns`) also claim pytest, Vitest and Go work from `unit-testing` and `test-gap-audit` |
| Its `dotnet` plugin has the modern Roslyn LSP | That same plugin carries `csharp-expert`, a router that tells the model to install more `dotnet-agent-skills` plugins, and its `msbuild` entry; no way to take the LSP alone |
| | Allowlisting is per marketplace: it exposes all 16 plugins to every adminhead plugin, against decision 2 ("cross-marketplace dependencies stay minimal") |
| | Agents are Copilot `.agent.md` files (`agents:` handoffs, `user-invocable`), not native subagents; the plugins also read repo overlay files (`.agents/skill-overlays/...`) |

Decision: port. Mitigate staleness by recording the upstream commit (`10d85e2`) and source paths in each plugin's NOTICE, so a later `git diff 10d85e2..HEAD -- plugins/<upstream>/skills/<name>` shows what to pull in. Users who want an upstream specialist we don't port (MAUI symbolication, WinForms, template engine) can install it directly; our names never reuse an upstream plugin name, so both can coexist.

## Naming

Decision 7 prefixes only collision-prone names. Here the main collision risk is upstream itself, since a user may install `dotnet-maui@dotnet-agent-skills` next to ours. Rule: **never reuse a `dotnet-agent-skills` plugin name** (`dotnet`, `dotnet-advanced`, `dotnet-ai`, `dotnet-aspnetcore`, `dotnet-blazor`, `dotnet-data`, `dotnet-diag`, `dotnet-experimental`, `dotnet-maui`, `dotnet-msbuild`, `dotnet-nuget`, `dotnet-template-engine`, `dotnet-test`, `dotnet-test-migration`, `dotnet-upgrade`, `dotnet-winforms`, `dotnet11`) or `csharp-lsp` (claude-plugins-official). Product names stay bare (`msbuild`, `nuget`, `blazor`, `maui`, `ef-core`, `aspnet-core`), matching `terraform` and `prisma`.

## Proposed plugins

All are skills (S). Sizes are SKILL.md lines; references load on demand. Every port: MIT LICENSE with "Copyright (c) .NET Foundation and Contributors" (plus any other source's holder), and a NOTICE listing upstream paths, the commit, and the modifications (the `dependency-vetting` NOTICE is the model).

## `dotnet-meta`

```json
{
  "name": "dotnet-meta",
  "description": "Plugin set for C# and .NET projects, installed at project scope. Ships no components of its own.",
  "dependencies": [
    "programming-core",
    "csharp",
    "msbuild",
    "dotnet-testing",
    "nuget",
    { "name": "omnisharp", "marketplace": "claude-code-lsps" }
  ]
}
```

Why these four: every .NET repo has C# code, project files, tests and packages, so each fires in ordinary sessions. `python-meta` includes `python-packaging` on the same reasoning, which is the precedent for `nuget`.

Direct installs, because only some .NET repos need them and a meta's members can't be turned off one by one: `aspnet-core`, `ef-core`, `blazor`, `maui`, `dotnet-upgrade-guide`, `dotnet-diagnostics`, `dotnet-performance`, `roslyn-analyzers`, `aspire`, and the optionals. `recommend-plugins` should propose them from evidence (`Microsoft.NET.Sdk.Web` → `aspnet-core`; `Microsoft.EntityFrameworkCore` → `ef-core`; `.razor` → `blazor`; `UseMaui` → `maui`; `BenchmarkDotNet` → `dotnet-performance`; `Microsoft.CodeAnalysis.CSharp` with `IsRoslynComponent` → `roslyn-analyzers`; `Aspire.Hosting` → `aspire`). Revisit a `dotnet-web-meta` (`dotnet-meta` + `aspnet-core` + `ef-core`) only if a real project wants all of it; decision 3 already rejected similar 3-plugin metas.

## Implementation plan

Four batches of 3-4 plugins for parallel implementers. Each implementer:

1. Reads `CLAUDE.md`, the README rules, decision 10 of the adoption plan, this design, and the `skill-authoring` skill.
2. Scaffolds with `scripts/plugins.py new <name> --kind skill --description "..."` (no `--meta`; batch 1's coordinator step registers the meta), copies only the named upstream files from `3rd-party/dotnet-skills` (read only, never runs its scripts), and rewrites.
3. Writes a description under ~350 characters in the house voice: what it does, then "Use for ..." with 3-5 concrete triggers, then "Not for ..." naming only adjacent adminhead plugins. No "ALWAYS USE"/"MUST USE".
4. Converts PowerShell command blocks to bash (keep a PowerShell form only where the tool is Windows-only), replaces `ask_user` with plain "ask the user", drops repo-overlay steps and `dotnet/skills` cross-links, renames upstream skill references to our plugin names, and points code navigation at codebase-memory (`search_graph`, `trace_path`) then the LSP tool.
5. Rechecks version-sensitive facts with Context7 or Microsoft Learn (.NET 10 GA features, .NET 11 preview status, MTP and `dotnet test` syntax in the .NET 10 SDK, xUnit v3, MSTest v4, EF Core 10).
6. Adds LICENSE (MIT, .NET Foundation and Contributors, plus other holders) and NOTICE (upstream paths at `10d85e2`, modifications), 3-5 trigger evals with hard negatives against sibling .NET plugins and `unit-testing`/`coding`, then runs `claude plugin validate --strict plugins/<name>` and `python3 scripts/plugins.py check`.
7. Reports unverified facts and follow-ups in `docs/research/implementation-<date>/dotnet-batch-<n>.md`.
