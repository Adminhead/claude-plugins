# Eval run, 2026-10-21 (vet)

Trigger evals for the new `vet` plugin (`plugins/vet/evals/`, 6 cases: 2 positive, 4 hard negatives), run once each with `claude plugin eval plugins/vet --trust-plugin -j 3`.

## Results

- **First run: 4 of 6, and not a real result.** Both positives (`vet-links`, `vet-inbox`) failed with "Skill called 0x". The four negatives passed, but only because nothing could fire. The init record of the trace showed `plugin_errors: [{plugin: "vet@inline", type: "dependency-unsatisfied", message: "Dependency \"plugin-vetter\" is not installed..."}]`. The eval sandbox has no marketplace, so `"dependencies": ["plugin-vetter"]` can't resolve, and the plugin is dropped before the session starts.
- **Rerun on a scratch copy with the `dependencies` line removed (nothing else changed): 6 of 6.** Both positives fired `vet`, and all four negatives (npm package safety, installing plugin-vetter, Vitest vs Jest, auditing a third-party hooks.json) stayed quiet. Cost of both runs: $0.50 + $0.29.

## Decision

The dependency stays in `plugins/vet/.claude-plugin/plugin.json`. A real install of `vet@adminhead` pulls `plugin-vetter` from the same marketplace, so it only breaks the isolated eval sandbox. To re-run these evals, use a copy without the `dependencies` line, as above.

## Follow-up

`ship` and `forgejo-ship` also declare dependencies and ship evals. If their dependencies don't resolve in the sandbox either, their negative cases pass for the same empty reason. Check the init record of one trace (`--keep-temp`) before trusting those suites.
