# Third-party skills review

Date: 2026-10-02. Plan: [`docs/plans/third-party-skills-review.md`](../plans/third-party-skills-review.md).

This review reads eight third-party skill repos and decides, per skill, whether to add it as a new skill, mine it to enhance one of ours, or skip it. It also mines their evals for our `claude plugin eval` suites. Nothing here imports a skill; adoption is a later plan.

## Scope

- Compared against our 40 skills in the 12 migrated plugins, `ripgrep:ripgrep`, `secret-stash`, the user-level design skills, and the installed third-party plugins (`commit-commands`, `skill-creator`, `claude-md-management`, `code-review`, `frontend-design`, `sentry-cli`, `plugin-dev`, `avoid-ai-writing`, `exa`, `design`, `claude-mem`, built-ins).
- In-scope domains: the current stack, language-agnostic practice, and the infrastructure, operations, data, API, repo-workflow, tooling, quality and research categories in the plan. Java, .NET, Azure, GCP-specific, mobile, PHP, Ruby and business content are `skip-domain`.
- Method: description-only triage, then a full read of every candidate (SKILL.md, references, scripts) side by side with our target skill, then eval mining.

## How to read the tables

- **Source** is `repo:path`. Several sources in one cell were merged into one decision.
- **Proposed name** is `plugin:skill`. *(new)* marks a proposed new plugin.
- **Value** uses the rubric below. Rows sort by value, then by target plugin.
- **UNCONFIRMED** marks a claim the reviewers could not check against a primary source. Verify it before porting.
- Every non-skip review row lands in Table 1 or Table 2. Rows that supplement another pick are listed as extra sources on that pick's row.

## Value rubric

| Score | Meaning |
| --- | --- |
| 5 | Fills a real gap in frequent work, or materially corrects or deepens one of our skills. Low adaptation cost |
| 4 | Clear gain for frequent work. Moderate adaptation |
| 3 | Useful but occasional, or a strong idea that needs a heavy rewrite |
| 2 | Marginal. Narrow use, or mostly duplicates what we have |
| 1 | Barely worth recording. Kept for a single good idea |

## Eval sources

### Format mapping

Source evals come in `evals/evals.json` per skill (`cc-skills`, `cc-skills-golang`, `developer-platform-skills`). Each case has a prompt, a `trap` (the natural wrong default) or `expected_output`, and 5-14 atomic assertions.

| evals.json | `claude plugin eval` |
| --- | --- |
| `name` or `id` | case directory `evals/<skill>-<slug>/` and frontmatter `name` |
| `prompt` | `prompt.md` body. Inline any code the prompt needs, or ship it as a fixture |
| `trap` / `expected_output` | `expected_outcome` (restated as the correct behavior) and the opening line of the `llm` grader |
| MUST assertions | numbered must-list in an `llm` grader |
| "Does NOT" assertions | must-not list in the same grader |
| Mechanical assertions (a token present or absent) | `regex` graders with `target: last_message` |
| `trigger_queries` | routing cases: `tool_used` on `Skill` with `min`/`max`, `arm: both` for negatives |
| `files` fixtures | `context.add_dirs` in `case.yaml`, or `scaffold_script` (run with `--scaffold`) |
| WITH/WITHOUT harness | `--ablation with-without` (the default when a plugin resolves) |

Grader rules:

- Bundle 11-14 expectations into 3-5 graders by theme: one `llm` grader per trap, `regex` for unambiguous tokens, one `llm` completeness grader for the rest.
- Use `weight` on graders so the trap grader dominates the score.
- Write every `llm` grader to judge low when ambiguous and never reward length.
- Use `--judge-model` with a stronger model than the default haiku for quality evals. Runs default to 3; quality cases keep 3, routing cases use 1.
- Strip assertions that grade the source skill's taste (clockwork, testify, slog mandates, a fixed pin style). Any imported case that asserts a pin style must instead assert "follows repo convention".

### Converted example

Source: `cc-skills-golang/skills/golang-structs-interfaces/evals/evals.json` id 1. The 65% pass-without-skill figure is the skill-wide baseline in `cc-skills-golang/EVALUATIONS.md`; case 1 alone passed 2 of 5 assertions without the skill. The prompt below is adapted: it adds `Close` and `Verify` and asks for the layout and code. Target: `efficient:golang`.

`plugins/efficient/evals/golang-interface-at-consumer/prompt.md`

```markdown
---
name: golang-interface-at-consumer
description: Quality. Where to define the interface between a notification package and an email client.
tags: [quality, golang]
runs: 3
max_turns: 3
allowed_tools: [Read, Glob, Grep, Skill]
expected_outcome: The interface lives in the consuming package, lists only the methods it calls, and the email package keeps exporting a concrete struct.
---

I'm writing a Go notification service. An `email` package has a `Client` struct with `Send`, `Close` and `Verify`. A `notification` package needs to send email. Where should I define the interface? Show the package layout and code in your reply.
```

`graders/placement.md`

```markdown
---
type: llm
weight: 3
---
Pass only if all hold:
1. The interface is defined in `notification`, the consumer.
2. It lists only `Send`, not `Close` or `Verify`.
3. `email` keeps exporting the concrete `Client` and exports no interface for it.
4. The answer says why: the consumer owns the contract.
Fail if it puts the interface in `email`, mirrors the whole `Client` API, or proposes a shared `interfaces` package.
If the answer is ambiguous, fail it. Do not reward length.
```

`graders/no-implementor-interface.md` (mechanical companion; keep only if runs show no false fails)

```markdown
---
type: regex
pattern: 'package email[^`]{0,400}type \w+ interface'
match: not_contains
target: last_message
weight: 1
---
```

`match` defaults to `contains`, which would reward the trap, so the grader sets `match: not_contains` to fail when an interface appears in the `email` package. The ``[^`]{0,400}`` span cannot cross a closing code fence, so the match stays inside one code block (plugin-evals grader reference).

### Methodology to adopt

- **Write the trap first.** A case tests the natural wrong default, not an explicit wrong instruction. Do not name the problem category in the prompt (cc-skills `CLAUDE.md`).
- **Pre-flight without the skill.** Drop cases where both arms pass; split cases where both arms score the same partial result. Keep capability suites near 50-80% baseline (phoenix-evals saturation rule).
- **Keep teammate pressure.** About a third of the Go cases embed a plausible wrong suggestion; the skill should make the model push back.
- **One behavior per grader.** Pair each must with a named must-not, and add one "explains why" check.
- **Contaminated baselines.** `--ablation with-without` drops the whole plugin, so sibling skills in the same plugin are already absent from the without arm. The risk is skills from other installed plugins or user-level skills that cover the same ground (golang, testing, problem-solving). Add `tool_used` graders with `max: 0` and `arm: both` for those skills.
- **Two classes.** Tag `capability` (new-skill delta) and `regression` (routing must not move); gate with `--tag` and `--threshold`. Release-critical regression cases need every run to pass (pass^3).
- **Validate the judge once.** Hand-label a small set of saved `--json` outputs and check agreement before trusting an `llm` grader (phoenix-evals validation.md).
- **Error analysis first.** Write evals for observed failures, not imagined ones (eval-driven-dev, phoenix axial coding).
- **Baselines.** Commit a small `baseline.json` extracted from `--json` per skill version, since results directories are gitignored (ECC eval-harness).
- **Hold-outs.** Tag a few cases `held-out` and keep them out of skill-tuning loops.
- **Cost.** Start at `runs: 1` and `--max-cost-usd` for a first pass, then return to the default 3.

## Adaptation rules for ported skills

From the Sonnet 5.5 and Opus 5.5 prompting guidance and the best-practices page:

- Rewrite CRITICAL, YOU MUST, ALWAYS and NEVER as plain imperatives with one stated reason each. Keep real safety rules, specific.
- Delete thoroughness boosters ("be thorough", "if in doubt use X", "use this tool for everything"), tool-minimizing rules, prefill tricks and "think step by step" instructions.
- Delete older-model workarounds with no current evidence. Do not import model-specific snippets without a routing or task eval on the target model.
- Turn "don't X" lists into "do Y because Z", merge duplicates, and cut anything already in `~/.claude/CLAUDE.md`.
- Keep numbered steps only where order or completeness matters. Keep decision rules and exact commands.
- Rewrite descriptions as What / Use when / Not for. Remove pushy trigger language and check against sibling skills.
- Note any assumed effort level or model, and verify coder-style skills at the effort the agents actually run.
- Strip personas, interviews, rankings, memory-file instructions, sub-agent fan-out boilerplate and cross-references to the source repo's sibling skills.

Claude Code fit:

- Replace foreign tool names: `AskQuestion` with `AskUserQuestion`; `mcp__github__*` tables with `gh`; Playwright MCP `browser_*` tools with `playwright-cli` or claude-in-chrome; drop Copilot-only calls (`renderMermaidDiagram`, Joyride `joyride_request_human_input`, `web_search`).

- Strip non-Claude-Code frontmatter (`metadata.openclaw`, Copilot `applyTo`, foreign `allowed-tools` lines).
- Writes to shared state (issues, labels, PRs, rulesets, releases, pushes, history rewrites, settings) need explicit user approval. Commit only on request.
- Library and version claims go through Context7 before porting. Every UNCONFIRMED item in the tables is a port-time check.

Secret handling:

- Never copy example keys, tokens or connection strings from sources. Before commit, grep each port for secret-stash placeholder IDs.
- Secrets go to runtime injection (host env, Docker secrets or a secret manager) or a gitignored `.env` that `.dockerignore` excludes. Never put them in images, logs, committed Compose files or shell history. Env values are readable through `docker inspect`, so prefer file-mounted secrets for sensitive ones.
- Read-only skills deny secret-reading verbs (for example `get-secret-value`, `ssm get-parameter --with-decryption`).
- A credential pushed to a remote is compromised even after history rewrite: rotate it.
