**Pinning**

- Both steps use mutable branch refs (`@master`, `@main`). Every run pulls whatever is on the branch at that moment, so a breaking change or a compromised push reaches your CI immediately. They also make builds non-reproducible.
- Strictly, your CONTRIBUTING.md rule covers *third-party* actions, and `actions/*` are GitHub-owned. Even so, branch refs are worse than either a tag or a SHA. Pinning these to a SHA is the safest reading of the policy, and it keeps the workflow consistent if you later add a real third-party action.
- `actions/checkout@master` may not resolve at all, because that repo's default branch is `main`. Check this against the repo before relying on it.

**Suggested form**

```yaml
steps:
  - uses: actions/checkout@<full-40-char-sha> # v<x.y.z>
  - uses: actions/setup-go@<full-40-char-sha> # v<x.y.z>
    with:
      go-version-file: go.mod
```

I haven't filled in the SHAs, because I can't verify them from here. Look up the commit behind the release tag you want, for example with `gh api repos/actions/checkout/git/ref/tags/<tag>`. If the tag is annotated, dereference it to the commit. Dependabot's `github-actions` ecosystem can then keep the SHAs and version comments updated.

**Other issues**

- `go-version: stable` floats to the newest Go release, so a new Go version can break CI without any change in your repo. Prefer `go-version-file: go.mod`, or pin an explicit version.
- There's no `permissions:` block visible. Set `permissions: contents: read` at the workflow or job level so the token is least-privilege.
- `actions/checkout` persists the token in `.git/config` by default. If no later step needs to push, add `with: persist-credentials: false`.
- `setup-go` caches by default, which is fine. If you build with multiple `go.sum` files, set `cache-dependency-path`.

Issues, most serious first:

1. **Unpinned refs, which violates CONTRIBUTING.md.** Both actions point at moving branches (`@master`, `@main`) instead of a full 40-character commit SHA with a version comment. Whatever lands on those branches runs in your workflow with access to the job's `GITHUB_TOKEN` and any secrets. A compromised or buggy upstream commit would flow straight into your CI.

2. **Branch refs are unstable.** Builds aren't reproducible. A push to either branch can change or break your pipeline with no change in your repo. Both `actions/checkout` and `actions/setup-go` publish version tags, and branch heads can contain unreleased work.

3. **`go-version: stable` floats.** Every run uses whatever Go release is current. A new Go release can break your build or tests unexpectedly. Prefer one of these:
   - `go-version-file: go.mod`, so CI matches what the project declares.

4. **No `permissions:` block (not visible in this snippet).** If the workflow doesn't set a restrictive `permissions:` (for example `contents: read`), it may get broader token scopes than it needs.

5. **Checkout persists credentials (minor).** `actions/checkout` leaves the token in the local git config by default. If no later step needs to push, add `persist-credentials: false`.

## Workflow

Save this as `.github/workflows/dependabot-auto-merge.yml`:

```yaml
name: Dependabot auto-merge

on: pull_request

permissions: {}

jobs:
  auto-merge:
    runs-on: ubuntu-latest
    if: github.event.pull_request.user.login == 'dependabot[bot]' && github.repository == 'OWNER/REPO'
    permissions:
      contents: write        # needed to enable auto-merge
      pull-requests: write
    steps:
      - name: Fetch Dependabot metadata
        id: meta
        uses: dependabot/fetch-metadata@v2   # pin to a full commit SHA in practice
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}

      - name: Enable auto-merge for minor and patch updates
        if: >-
          steps.meta.outputs.update-type == 'version-update:semver-minor' ||
          steps.meta.outputs.update-type == 'version-update:semver-patch'
        run: gh pr merge --auto --squash "$PR_URL"
        env:
          PR_URL: ${{ github.event.pull_request.html_url }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Replace `OWNER/REPO` with your repository. The repository check stops the job from running on forks.

**Required repo settings.** The workflow does nothing useful without these:
1. Go to Settings → General and enable **Allow auto-merge**.
2. Add a branch protection rule or ruleset on `main` with **required status checks**. This is what makes "once CI passes" true.

## Security concerns

1. **Without required checks, auto-merge merges immediately.** `gh pr merge --auto` only waits for checks that branch protection requires. If none are required, the PR merges at once. This is the most common mistake.

2. **Don't use `pull_request_target`.** It runs with a write token and secrets in the base repo context. Combined with a checkout of PR code, it is a well-known way to take over a repo. The plain `pull_request` event is enough here. Dependabot-triggered runs get a restricted token and only Dependabot-scoped secrets. The workflow never checks out or executes PR code.

3. **Check the PR author, not just `github.actor`.** The `user.login` condition is the safer gate. `github.actor` changes to whoever last pushed or re-ran the PR, and the `dependabot[bot]` identity is the only thing that should unlock the merge step. Don't use name-based checks like `startsWith(head_ref, 'dependabot/')`, because anyone can create a branch with that name.

4. **Semver labels are only as trustworthy as the maintainer.** A compromised maintainer account or a malicious patch release (typosquat takeovers, `event-stream`-style incidents) still looks like a patch bump. Auto-merging means unreviewed third-party code lands in `main` and may ship. Ways to reduce the risk:
   - Add a `cooldown` (e.g. `default-days: 3–7`) in `dependabot.yml`. Most malicious releases are caught and yanked within days.
   - Limit auto-merge to dev dependencies or low-risk ecosystems with `steps.meta.outputs.dependency-type` or `package-ecosystem`.
   - Exclude `0.x` packages. Semver doesn't hold there, and minor bumps often break things.

5. **Your tests are the only safety net.** If coverage is thin, a breaking minor or patch release will merge cleanly. Be especially careful with lifecycle scripts (`postinstall`), which run in CI before tests do.

6. **GitHub Actions updates are higher risk.** If the `github-actions` ecosystem is in your `dependabot.yml`, auto-merging action bumps lets third-party code run with your workflow tokens and secrets. Either exclude that ecosystem from auto-merge or pin actions by SHA and review those PRs manually.

7. **Grouped updates.** If you use Dependabot `groups`, check how `update-type` is reported for a group that mixes bump levels. Confirm that a major bump can't slip through inside a group. The safe approach is to group only minor and patch updates in `dependabot.yml`.

8. **Least privilege and pinning.** Keep `permissions: {}` at the top level and grant write only to this job. Pin `dependabot/fetch-metadata` to a commit SHA. Pass `html_url` through `env` rather than interpolating it into the script, which avoids injection from untrusted context values.

9. **Review requirements.** If branch protection requires an approving review, auto-merge will wait forever. Don't "fix" that by having the workflow approve its own PRs. That defeats the review control. Use a ruleset that exempts the Dependabot bypass actor only if you accept the risk.

10. **Merge visibility.** Auto-merged changes bypass human eyes, so enable Dependabot alerts and a periodic audit (`npm audit`, `pip-audit`, etc.) in CI. Also consider notifications on merges to `main` so you notice unexpected changes.

        run: gh pr merge --auto --squash "$PR_URL"
        env:
          PR_URL: ${{ github.event.pull_request.html_url }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

1. Settings → General → enable **Allow auto-merge**.
2. Add a **branch protection rule or ruleset** on `main` that requires your CI status checks to pass. `gh pr merge --auto` only waits for *required* checks. If none are required, the PR merges immediately.
3. Consider requiring one approval. The workflow doesn't approve anything. If you want that, add a `gh pr review --approve` step, but see the concerns below.

**Security concerns**

1. **Auto-merge is only as safe as your required checks.** If CI is thin, a malicious or broken update ships. Minor and patch updates are not guaranteed safe, because semver is a convention and not enforced.
2. **Supply chain risk.** A compromised maintainer or a hijacked package can publish a "patch" release containing malware. Auto-merge puts it into `main` with no human review. Mitigations:
   - Set a Dependabot `cooldown` (for example 3–7 days) in `dependabot.yml`, so freshly published versions have time to be caught and yanked.
   - Pin lockfiles and use `npm ci` or the equivalent.
   - Restrict auto-merge to dev dependencies or to specific ecosystems if you want to be more conservative. `dependency-type` from the metadata action lets you do this.
3. **Don't use `pull_request_target`.** It runs with write permissions and secrets in the base repo context. Combined with checking out PR code, that's a well-known privilege escalation. `pull_request` is correct here. Dependabot-triggered `pull_request` runs get a read-only token by default and no repo secrets, and the job's `permissions` block is what grants write.
4. **Gate on the PR author, not `github.actor`.** The `actor` can be whoever last pushed or re-ran the workflow. A human could push to a Dependabot branch and inherit the bot's trust. Checking `pull_request.user.login` is stricter. Combined with the `update-type` check, it keeps this narrow. Be aware that the `update-type` output is computed from the commit and PR metadata.
5. **Least privilege.** The top-level `permissions: {}` plus job-level grants keeps the token narrow. Note that `contents: write` is broad. The auto-merge feature requires it, so rely on branch protection to constrain what actually lands.
6. **Pin third-party actions to a full commit SHA.** Tags like `@v2` are mutable. Dependabot can also keep the SHA pins updated for `github-actions`.
7. **Auto-merging GitHub Actions updates is itself risky.** Updating a workflow action changes code that runs with your tokens. Consider excluding the `github-actions` ecosystem from auto-merge, for example by checking `steps.metadata.outputs.package-ecosystem != 'github-actions'`.
8. **Bypass settings.** If admins or bots can bypass branch protection, auto-merge can bypass your checks too. Review who is in the bypass list.
9. **Approval caveat.** If you add an auto-approve step and also require one approval, the bot satisfies the review rule on its own. That makes the "required review" rule meaningless for these PRs. Be deliberate about that.
10. **Major updates and security advisories.** Major updates are excluded by the condition. Group updates can mix update types, so check how `fetch-metadata` reports grouped PRs. If you use groups, test it first or split minor and patch groups from major ones.
