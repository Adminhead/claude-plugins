# Breaking-change policy

## Principle

A change is **breaking** if a client written correctly against our documentation could stop working after it. A change is **non-breaking** if it can't do that. Breaking changes ship only in a new major version (`/v2`). Non-breaking changes ship into the current version at any time. If a PR is breaking, it needs a new version, and it needs sign-off from the API governance owner (see Governance).

"Correctly written" means the client follows the rules in *Client obligations* below. Behavior we haven't documented is not contract, and we will say so explicitly rather than leave it to be inferred.

## Client obligations

Clients of the v1 API must:

- Ignore response properties they don't recognize.
- Treat every enum value in a response as potentially unknown, and handle unknown values gracefully. They must not crash or silently misroute.
- Not depend on the length, format, or structure of opaque strings (IDs, cursors, tokens).
- Not depend on the order of items unless the documentation specifies one.
- Not parse error messages. They branch on the HTTP status and the error `type` or `code`.

Our docs and OpenAPI spec state these rules. They are what make the non-breaking list below safe.

## Breaking changes (require a new version)

- Removing or renaming an endpoint, HTTP method, response field, or request parameter.
- Changing the type, format, or meaning of an existing field, including narrowing the range of values we return or widening what we reject.
- Removing an enum value, or changing what an existing value means.
- Adding a required request parameter, or making an optional one required.
- Making validation stricter for input that was previously accepted.
- Changing the HTTP status code, content type, or error `type`/`code` for an existing scenario.
- Changing a documented default, a documented sort order, pagination semantics, or authentication or authorization requirements.
- Making a previously always-present response field sometimes absent or `null`.
- Removing an event type, or removing or renaming a field from a webhook payload.
- Tightening rate limits below the documented limit.

## Non-breaking changes (ship in the current version)

- Adding a new endpoint, resource, or optional request parameter.
- Adding a new response field.
- Adding a new value to a response enum. All enums are **open** unless the spec marks them `closed`. We expect to mark very few as closed, and a closed enum can never gain values within a version.
- Adding a new webhook event type or a new field in a webhook payload.
- Adding a new error `code` for a scenario that previously had none. Existing scenarios keep their existing codes.
- Changing the order of properties in a JSON object.
- Changing the length or format of opaque strings.
- Loosening validation, or making a required parameter optional.
- Improving performance, or changing latency within normal bounds.

## Decisions on the disputed cases

| Change | Verdict | Why |
| --- | --- | --- |
| New value in a status enum | **Non-breaking** | Enums are open and clients must tolerate unknown values. Removing or redefining a value is breaking. |
| Rename a field, keep the old one for a while | **Adding the new name is non-breaking. Removing the old name is breaking.** | During the overlap, both names work, so nothing fails. Within v1, the old field is marked deprecated and keeps working for the life of v1. It is removed only in v2. |
| Change error message wording | **Non-breaking** | The `message`/`detail` text is for humans and is not contract. The HTTP status and `type`/`code` are contract. |
| Change item order in a list | **Non-breaking, unless the order is documented** | If an endpoint documents a default sort or accepts a `sort` parameter, that order is contract. Otherwise we make no ordering promise. |

Two clarifications apply to these rules:

- **Renames are a deprecation, not a free change.** A rename is two steps: add the new field (non-breaking), then remove the old one at the version boundary (breaking). Marking the old field deprecated doesn't permit removing it early.
- **Unordered really means unordered.** Where order is unspecified, we may change it without notice. If a customer needs a stable order, the fix is to document and support a `sort` parameter, and the fix is not to freeze undefined behavior.

## Not contractual (may change without notice)

- Text of error messages and other human-readable strings.
- Order of items where no order is documented.
- Order of properties in JSON objects.
- Exact timing, latency, and the number of internal requests behind an operation.
- Length and format of opaque IDs, cursors, and tokens.
- Undocumented endpoints, fields, headers, and behaviors, even ones that happen to work.

Hyrum's Law applies: if enough customers use us, someone will depend on anything observable. When we learn that a customer depends on something in this list, the right response is to document it (making it contract) or to tell them it's unsupported. Silently keeping it frozen isn't an option. We don't treat an observed dependency as contract.

## Security exception

We may change the behavior of any version, without a version bump, when needed to fix a critical security or privacy issue. We will give as much notice as the situation allows and record the change in the changelog.

## Applying this in review

When a PR touches the API contract (the OpenAPI spec, response serializers, validation, error codes, or webhook payloads):

1. The CI OpenAPI diff (e.g. oasdiff) runs and flags anything on the breaking list.
2. A flagged PR can't merge into v1. It either gets reworked into an additive form (for example, add the new field and deprecate the old one) or moves to the next version.
3. If a reviewer believes a flagged change is safe, the API governance owner decides and records the reason in the PR. The reviewer doesn't decide alone.
4. If the change isn't on either list, the default is to treat it as breaking until the owner rules, and then to add it to the list so the question stays settled.

# API Compatibility Policy

## Principle

A change is **breaking** if a client written correctly against our documented contract could stop working after it ships. A change is **non-breaking** if such a client keeps working unchanged.

The **contract** is what the OpenAPI spec and published docs state: endpoints, methods, parameters, field names, types, nullability, documented enum values, status codes, error `code` values, documented ordering, and documented limits. Anything not in the contract (message prose, unspecified ordering, undocumented fields) is not covered, even if some client happens to depend on it.

Breaking changes ship only in a new major version (`/v2`). Non-breaking changes ship in `v1` at any time.

## Rules clients must follow

These are published in the public docs. The non-breaking rules below depend on them.

1. **Ignore unknown fields** in responses.
2. **Treat all response enums as open.** Handle unknown values gracefully, for example by falling back to a default.
3. **Don't parse error `message` text.** Branch on the HTTP status and the error `code`.
4. **Don't rely on ordering** unless the docs specify it.

If a PR needs a rule that isn't published, publish it first. Otherwise we can't treat the change as non-breaking.

## Breaking changes (require a new version)

- Removing or renaming an endpoint, method, parameter, or response field.
- Changing a field's type, format, or units. This includes widening `int` to `string` and changing the ID format.
- Making a response field nullable or optional when it was guaranteed present.
- Making an optional request field required, or adding a new required request field or parameter.
- Tightening request validation: narrower accepted values, lower max length, new constraints.
- Removing a value from a request enum, or removing a documented response enum value.
- Changing the meaning of an existing field, enum value, or endpoint behavior.
- Changing HTTP status codes for existing outcomes, or changing or removing an error `code`.
- Changing documented ordering, a documented default (page size, sort, filter), or the pagination mechanism.
- Adding authentication or authorization requirements to an existing endpoint, or requiring a new scope.
- Lowering documented rate limits or size limits.
- Removing a deprecated field, endpoint, or value (see "Renames and deprecation").

## Non-breaking changes (allowed in v1)

- Adding a new endpoint, resource, or HTTP method.
- Adding a new response field, response header, or optional request parameter. The default must preserve the old behavior.
- Adding a new value to a **response enum**.
- Adding a new value to a **request enum**, since existing clients never send it.
- Loosening request validation, or making a required request field optional.
- Making a response field non-nullable or guaranteed present, when it was previously optional or nullable.
- Changing error `message` text, or adding fields to the error body.
- Changing the order of items where the docs don't specify one.
- Raising rate limits or size limits.
- Performance changes and bug fixes that bring behavior in line with the documentation.
- Marking something deprecated, as long as it keeps working.

## Specific cases

**New value in a status enum.** This is non-breaking for responses, because clients must treat enums as open (rule 2). It becomes breaking if the new value changes the meaning of existing ones, for example splitting `active` so that some records no longer match it. If a PR adds a response enum value, call it out in the changelog so integrators aren't surprised.

**Renaming a field and keeping the old one.** Adding the new name is non-breaking. The rename is only finished when the old name is removed, and *removal is breaking regardless of any deprecation period*. The period is the migration path. It doesn't change the classification. So:
- Ship both fields with identical values, and mark the old one deprecated in the spec and docs.
- Remove the old field only in the next major version.

**Changing error message wording.** This is non-breaking. Messages are for humans and may change at any time. Changing the HTTP status or the `code` is breaking.

**Changing item order in a list.** If the docs specify an order (such as `created_at desc`), changing it is breaking. If they don't, it's non-breaking. List endpoints should either document a default order or state explicitly that order is unspecified. Pagination must stay stable and complete either way.

## Grey areas: default to breaking

If a change doesn't clearly fit above, treat it as breaking until the API owner decides otherwise. Common cases:
- Behavior changes that don't alter the schema, such as a different default filter, a different side effect, or changed idempotency.
- Latency changes large enough to hit client timeouts.
- Changing the format of opaque values (cursors, tokens) that we've documented as opaque. This is non-breaking, but only if they really were documented as opaque.

**Security exception:** a fix for a vulnerability may ship in `v1` even if it's technically breaking. It needs sign-off from the API owner and security, plus advance customer notice where possible.

## Process

- Every PR that touches the API spec or response and request shapes states in its description: **breaking / non-breaking / unsure**, with a one-line reason referencing this policy.
- Run an OpenAPI diff in CI (for example `oasdiff`) and fail the build on breaking findings. Overriding it requires API-owner approval.
- Breaking changes go on the `v2` branch. Don't merge them into `v1`.
- Deprecations are announced in the changelog and via `Deprecation`/`Sunset` headers. State the earliest removal date, and give at least [6/12] months' notice before a major version is retired.
