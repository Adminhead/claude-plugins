**Short answer: the marketing wording can't stay.** "Every event is delivered exactly once, in order" is false for this design, on both counts.

- **Not exactly once.** Retries on non-2xx, plus timeouts and crashes, make this at-least-once. If a customer processes an event and then crashes or times out before replying, we send it again. Exactly-once delivery over HTTP isn't achievable. What customers can get is exactly-once *processing*, by deduplicating on the stable event ID.
- **Not in order.** Parallel workers and retries reorder events. If event A fails and is retried while B succeeds, B arrives first. Strict ordering would need one in-flight delivery per endpoint. A single failing delivery would then block everything behind it, which is a different design.

**Wording marketing can use instead:** "Every event is delivered at least once, with automatic retries for up to ~3 days. Each event carries a stable ID so you can safely deduplicate." That is a real strength and it's accurate.

If marketing needs ordering, engineering would have to build an opt-in per-endpoint FIFO mode. Don't promise it until it exists.

## Draft: Delivery guarantees

### Summary

- **At-least-once delivery.** We deliver every event to each subscribed endpoint at least once. An event may be delivered more than once.
- **Best-effort ordering.** Events are not guaranteed to arrive in the order they occurred.
- **Stable event ID.** Every delivery carries the same `webhook-id` for a given event, across all retries. Use it to deduplicate.

### At-least-once delivery

We treat a delivery as successful only when your endpoint returns a `2xx` response within the timeout. If we don't get one, we retry. This means you may see the same event more than once, for example when your server processes an event and then crashes or times out before it responds.

**Make your handler idempotent.** Record the `webhook-id` of each event you process. If you receive an ID you've already handled, return `2xx` and skip the work.

### Ordering

Events can arrive out of order. We deliver through parallel workers, and a failed delivery is retried later while newer events continue to flow. Don't rely on arrival order or on `timestamp` to infer sequence. To get the current state of a resource, fetch it from the API when you receive an event rather than applying events as a sequence of changes.

### Response handling and timeouts

| Your response | What we do |
|---|---|
| `2xx` | Success. No further attempts. |
| `3xx` | Treated as a failure. Update your endpoint URL. |
| `408`, `429`, `5xx`, timeout, connection error | Retry on the schedule below. We honor `Retry-After` on `429` and `503`. |
| `410 Gone` | We disable the endpoint. |
| Other `4xx` | Not retried. The event moves to the dead-letter queue. |

We wait up to **[15–30] seconds** for a response. Queue the work and acknowledge quickly instead of processing inline.

### Retry schedule

Failed deliveries are retried with exponential backoff and jitter. **[Engineering to confirm the exact schedule.]** For example, 10 attempts over about 75 hours, with intervals growing from seconds to many hours. Each retry carries the same `webhook-id`.

### When delivery fails permanently

If all retries fail, the event goes to a dead-letter queue and is kept for **[7–30] days**. You can inspect it in the dashboard and redeliver it. If an endpoint keeps failing, we disable it and notify you by email. Events are not delivered to a disabled endpoint until you re-enable it. **[Engineering to confirm what happens to events during the disabled period.]**

### Recovering missed events

- Use the delivery log in the dashboard to see every attempt, with headers, body, response code, and timing.
- Redeliver individual events, or replay a range after an outage.
- For high-stakes events such as payments, reconcile against the API periodically. Webhooks are a notification channel, and the API remains the source of truth.

# Can the marketing wording stay?

No. "Exactly once, in order" contradicts the design in two ways.

- **Not exactly once.** Retrying on non-2xx makes this at-least-once delivery. If the receiver processes an event and its 200 response is lost or times out, we retry and it sees the event twice. True exactly-once delivery isn't possible over an unreliable network. What you can offer is at-least-once delivery plus a stable event ID, which lets receivers get exactly-once *processing* by deduplicating.
- **Not in order.** Parallel workers and retries both reorder events. Event B can be delivered while event A is waiting for a retry, and a retried A then arrives after B.

**Wording that is true and still sells:**
> "Every event is delivered at least once, with automatic retries and a stable event ID so you can safely process each event exactly once."

Don't use "guaranteed delivery" without qualification either. Retries are bounded, so an endpoint that is down long enough will lose events unless you offer replay.

If marketing wants real ordering, engineering would need per-key serialization, such as routing all events for one resource to one worker and blocking on retry. That costs throughput and causes head-of-line blocking. I'd recommend against it. Ship sequence metadata instead (see the last section).

# Draft: Delivery guarantees

## Summary

| Property | Guarantee |
|---|---|
| Delivery | **At least once.** Every event is retried until your endpoint acknowledges it or retries are exhausted. |
| Duplicates | **Possible.** The same event may be delivered more than once. |
| Ordering | **Not guaranteed.** Events may arrive out of order. |
| Identity | Every event has a stable `id` that is identical across all delivery attempts. |

## Delivery and retries

We deliver each event with an HTTP `POST` to your endpoint. A response with a `2xx` status code means success. Any other outcome counts as a failure and triggers a retry. This includes non-2xx responses, connection errors, and timeouts longer than `[N]` seconds.

We retry failed deliveries `[up to N times over N hours, with exponential backoff]`. After that, the event is marked failed `[and can be replayed from the dashboard/API]`.

Return a `2xx` as soon as you have durably accepted the event, ideally before doing slow work. If your handler is slow, we may time out and retry an event you actually processed.

## Duplicates

Because we retry on any failure, including a lost acknowledgment, your endpoint may receive the same event more than once. Every attempt for an event carries the same `id`. Use it to deduplicate:

1. On receipt, check whether you've already processed `id`.
2. If so, return `2xx` and do nothing.
3. If not, process the event and record the `id`, ideally in the same transaction as your side effects.

Handled this way, each event takes effect exactly once on your side.

## Ordering

Events are delivered by parallel workers and may arrive in a different order than they occurred. A retried event can arrive after later events. Don't assume arrival order reflects the order of occurrence.

To handle this:
- Use `[created_at / sequence]` in the payload to determine the true order of events.
- For state changes, prefer fetching the current resource state from the API over applying events as deltas.
- Make handlers tolerant of stale events. For example, ignore an update older than the one you've already applied.

## Best practices

- Respond quickly with `2xx`, and process asynchronously.
- Make handlers idempotent.
- Store processed event IDs for at least `[retry window + margin]`.
- Monitor for failed deliveries `[via dashboard/alerts]`.
