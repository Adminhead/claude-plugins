# Review of the first draft

`HMAC-SHA256(secret, body)` in `X-Signature`, with one secret per endpoint, has a sound core. Per-endpoint secrets and HMAC are the right choices. It has four gaps:

1. **No replay protection.** The signature covers only the body, so a captured request stays valid forever. An attacker who sees one delivery can resend it indefinitely.
2. **No stable event ID.** Receivers have nothing reliable to deduplicate on. Delivery is at-least-once, so retries will produce duplicates. If receivers build without an ID, you can't fix that later.
3. **A single secret forces revoke-then-deploy rotation.** Either the customer's endpoint rejects valid deliveries for a while, or they skip rotating.
4. **Verification advice is missing.** Most real-world failures are receiver bugs, not crypto weaknesses.

# Scheme to ship: Standard Webhooks 1.0.0

Use the open spec rather than a bespoke format. Customers get existing libraries, and you avoid designing the edge cases yourself.

**Headers on every delivery**
- `webhook-id`: one stable ID per event, identical across retries.
- `webhook-timestamp`: integer Unix seconds, set when the attempt is sent.
- `webhook-signature`: `v1,<base64>`, with several space-separated entries during rotation.

**Signed content**
```
signed_content = "{webhook-id}.{webhook-timestamp}.{raw_body}"
signature      = "v1," + base64(HMAC-SHA256(secret, signed_content))
```
Signing the timestamp is what gives replay protection. Signing the ID stops an attacker from swapping the ID header to defeat deduplication.

**Secrets**
- One secret per endpoint, generated by you with at least 192 bits of entropy.
- Use a `whsec_` prefix so secret scanners can find leaks.
- Store the secret so you can sign with it. This is different from API keys, where you store only a hash.
- Optional later: ed25519 signing (`v1a`) for enterprise customers who don't want to hold a shared secret.

**Payload**
Include `type`, an ISO 8601 `timestamp` of when the event occurred, and `data`. Put the event name in one place only.

# Zero-downtime rotation

1. The customer clicks "Roll secret" in the dashboard or calls the API. You generate a new secret and keep the old one active with an expiry. The customer chooses the overlap, with a default of 24 hours and a maximum of about 7 days.
2. During the overlap, sign every delivery with both secrets. The header becomes `webhook-signature: v1,<sig_new> v1,<sig_old>`.
3. The customer deploys the new secret on their own schedule. Verifiers accept a request if any listed signature matches a secret they hold, so it works whether they have deployed or not.
4. The old secret expires automatically at the deadline. An "expire now" action covers a suspected leak.
5. Show the old secret's expiry and a last-used indicator in the dashboard. Also surface a rotation-in-progress state, so nobody forgets to finish.

Rules:
- Never auto-rotate without the customer's action.
- Emergency rotation is the same flow with the overlap set to zero. Warn that deliveries will fail until the new secret is deployed.
- Rotate per endpoint, not per account.

# What the docs must tell receivers

The docs need runnable verification snippets in your supported languages. They should also state each of these:

1. **Verify every request, and reject failures with a 4xx.** Treat unsigned requests as hostile.
2. **Verify against the raw body bytes before any JSON parsing.** Re-serializing parsed JSON changes whitespace and key order, which breaks the signature. This is the most common integration bug. Frameworks with body-parsing middleware need a raw-body capture.
3. **Use a constant-time comparison** for signatures.
4. **Check the timestamp.** Reject anything more than about 5 minutes from the current time, in either direction. Keep clocks in sync with NTP.
5. **Accept any matching signature in the header,** because there can be several during rotation. Ignore unknown version prefixes rather than failing.
6. **Exempt the webhook route from session auth and CSRF middleware.** Otherwise the endpoint will reject all deliveries.
7. **Deduplicate on `webhook-id`.** Delivery is at-least-once. Never claim exactly-once.
8. **Don't rely on ordering or timestamps for ordering.** Retries and parallel workers reorder events.
9. **Acknowledge fast.** Return 2xx quickly and process asynchronously. State your timeout, for example 15–30 seconds, and the response-code behavior: 2xx is success, 3xx is a failure, and 410 disables the endpoint.
10. **Keep the secret out of logs, source control, and client code.** Load it from a secrets manager or environment variable.
11. **Reconcile high-stakes events** against your API periodically. A webhook is a notification, not a ledger.
12. **Test with the example-event tool and the delivery log** before going live.

# Related decisions to lock before launch

These aren't signing, but they are part of the contract:
- **Retries:** exponential backoff with jitter over about 3 days, with the exact schedule published. Dead-letter and replay should exist before launch.
- **SSRF:** validate endpoint URLs and resolved IPs against private ranges at delivery time, not just at registration.
- **Delivery log:** store headers as well as body for every attempt. Signature debugging needs the headers.

## Review of the first draft

`HMAC-SHA256(secret, body)` in `X-Signature` is sound as a primitive, but as a scheme it has these gaps:

1. **No replay protection.** A captured request with a valid signature stays valid forever. The timestamp has to be inside the signed payload.
2. **No event identity.** Receivers have nothing authenticated to dedupe on. Retries and replays look the same.
3. **No rotation path.** One secret per endpoint means a hard cutover, so either the sender or the receiver fails during the switch.
4. **No versioning.** If you ever change algorithm or format, you can't signal it.
5. **Underspecified format.** It doesn't say hex or base64, or how the receiver should compare.

## Scheme to ship

This follows the Standard Webhooks / Stripe pattern, so customers can use existing libraries.

**Headers on every delivery**

```
webhook-id:        evt_2Zk9...            # stable across retries of the same event
webhook-timestamp: 1759406400             # unix seconds, regenerated on every attempt
webhook-signature: v1,<base64> v1,<base64>  # space-delimited, one entry per active secret
```

**Signed content**

```
signed_payload = webhook-id + "." + webhook-timestamp + "." + raw_body
signature      = base64( HMAC-SHA256(secret_bytes, signed_payload) )
```

- `id` and `timestamp` are inside the MAC, so neither can be altered or stripped.
- `raw_body` is the exact bytes sent. Don't canonicalize JSON.
- Re-sign on each retry with a fresh timestamp and the same `id`. Otherwise retries after the tolerance window would always fail.
- The `v1,` prefix is the version. A future `v2` or an asymmetric `v1a` (Ed25519) can ride alongside it in the same header. Receivers ignore versions they don't know.

**Secrets**

- Generate them server-side from a CSPRNG, 32 bytes or more. Use a recognizable format such as `whsec_<base64>` so secret scanners can detect leaks.
- Keep one per endpoint, never shared across endpoints or customers.
- Store them encrypted at rest. They have to be recoverable because you need them to sign.
- Use separate secrets for test and live mode.

## Zero-downtime rotation

An endpoint can hold up to two active secrets.

1. The customer clicks **Rotate** (or calls the API). You generate secret B, and A stays active.
2. While both are active, you sign every delivery with both. The header carries two `v1,` entries.
3. The receiver accepts the request if any entry matches any secret it holds. Old code with A and new code with B both pass.
4. The customer deploys B everywhere, then clicks **Expire old secret**.
5. If they don't, A expires automatically after a grace period. Make the default 24 hours, configurable up to 7 days.
6. Add an **expire immediately** option for suspected compromise. It accepts the downtime in exchange for cutting off the leaked secret.

Also ship a "send test event" button, so customers can confirm B verifies before they expire A. Limit it to two active secrets so the header stays small and the state machine stays simple.

## What the docs must tell receivers

1. **Verify the raw body bytes, before parsing.** This is the most common failure. JSON middleware that re-serializes the body changes whitespace and key order, and the signature then fails. Give per-framework examples (Express `raw`, Flask `get_data()`, and so on).
2. **Use a constant-time comparison** (`hmac.compare_digest`, `crypto.timingSafeEqual`). Never use `==`.
3. **Enforce a timestamp tolerance**, 5 minutes by default, in both directions. Tell them to keep server clocks on NTP.
4. **Dedupe on `webhook-id`.** The timestamp check only narrows the replay window, and your own retries will also deliver the same event more than once. Handlers must be idempotent. Store seen IDs for at least the tolerance window, and ideally for your whole retry horizon.
5. **Accept multiple signatures** in the header, and ignore unknown version prefixes. This is what makes rotation work. A receiver that only reads the first entry will break during rotation.
6. **Reject on failure.** Missing headers, a bad signature, or a stale timestamp should return 4xx and process nothing. Don't log the secret or the full signature in error messages.
7. **Treat the secret like a password.** Keep it in a secrets manager, not in source control or client-side code. Rotate it on staff turnover or leaks.
8. **Use HTTPS only.** Signatures prove authenticity and integrity, not confidentiality.
9. **Ack fast.** Return 2xx quickly and process asynchronously, otherwise timeouts trigger retries.
10. **Don't rely on ordering.** Events can arrive out of order, so use the event's own data or timestamps.
11. **Prefer the official libraries.** Hand-rolled verification is where most bugs come from.

Publish test vectors too: a fixed secret, id, timestamp, body, and expected signature. This lets customers validate their implementation offline.

Offer Ed25519 asymmetric signing as `v1a,...` for customers who don't want a shared secret you must store, or who need to verify through untrusted intermediaries. The versioned header already leaves room for it.
