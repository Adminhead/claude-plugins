# Proposed error contract for the billing API

I haven't looked at your routes. This is based on the three shapes you described and on RFC 9457 and RFC 9110. Checking the routes against it is the first audit step.

## One envelope: RFC 9457 problem details

Send `Content-Type: application/problem+json` on every error, with an HTTP status that matches the failure.

```json
{
  "type": "https://api.example.com/errors/validation-error",
  "title": "Validation error",
  "status": 422,
  "detail": "Two fields failed validation.",
  "code": "validation_error",
  "errors": [
    {"field": "amount", "code": "out_of_range", "message": "amount must be > 0; received -5."}
  ],
  "retryable": false,
  "documentation_url": "https://docs.example.com/errors#validation_error",
  "request_id": "req_abc123"
}
```

- `title` stays the same for every occurrence of an error type. `detail` describes this specific occurrence.
- `code` is the string clients branch on. It is stable and must be listed in a published catalog.
- `errors[]` holds field-level detail. Each entry names the field, the value received, and the constraint violated.
- `request_id` goes in the body and in an `X-Request-ID` header.
- Never put stack traces, SQL or internal paths in a body.

**Migrating without breaking clients:** keep the old fields as extension members during the transition.
- Team A clients: also send `"error"`, with the same text as `title`.
- Team B clients: also send `"message"`, with the same text as `detail`.
- Team C clients: map `code: 1042` to `"legacy_code": 1042`, plus a new string `code`.
- Remove the legacy members only at a version boundary, with a deprecation notice.

## Status code rules

| Case | Status |
|---|---|
| Malformed JSON, wrong content type, bad query or path param syntax | **400** |
| Well-formed body that fails validation (missing field, out of range, bad format) | **422** |
| Business-rule violation (for example, refunding an already-refunded invoice) | **409** if it conflicts with current state, otherwise **422** |
| Missing or invalid credentials | **401** |
| Authenticated but not allowed | **403** |
| Resource not found | **404** |
| Idempotency key reused with a different payload | **422** (non-retryable) |
| Idempotency request still in flight | **409**, with `retryable: true` |
| Rate limited | **429**, with `Retry-After` |
| Unexpected server fault | **500** |
| Upstream or dependency failure, or overload | **502**, **503** or **504**, with `Retry-After` on 503 |

**Your 400-versus-422 split:** use 400 for requests that can't be parsed and 422 for requests that parse but are invalid. Your current mix of 400 and 422 for the same validation failure should become 422 everywhere. 400 for validation is also defensible, but only if applied everywhere. I recommend 422 because it separates "can't parse" from "parsed, but wrong".

**Never return 200 with `success: false`.** Clients, proxies, monitoring and retry logic all treat a 200 as success. The only exception is a bulk endpoint, where per-item results may appear inside a 200. Each failed item should reuse the same problem shape.

# Proposed error format: RFC 9457 Problem Details

Use `Content-Type: application/problem+json` on every non-2xx response.

```json
{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "2 fields are invalid.",
  "code": "validation_failed",
  "request_id": "req_8f3a...",
  "errors": [
    { "field": "amount", "code": "must_be_positive", "message": "amount must be > 0" }
  ]
}
```

- **Required:** `type`, `title`, `status`, `code`, `request_id`.
- **`code`:** a stable string, not an integer. Clients branch on it, and `type` is the same identifier as a URL.
- **`detail`:** human-readable and safe to show. Never put stack traces or internals in it.
- **`errors[]`:** only for field-level validation failures.
- **No success flag:** the HTTP status is the success signal. Any `{"success": false}` body is retired.
- **Legacy `code` 1042:** keep a mapping table from old numeric codes to new string codes. During migration, optionally add `legacy_code: 1042`.

# Status code per case

| Case | Status | `code` |
|---|---|---|
| Malformed JSON, wrong content type, unparseable body | 400 | `malformed_request` |
| Well-formed body that fails validation (missing field, bad value, bad format) | **422** | `validation_failed` |
| Missing or invalid credentials | 401 | `unauthenticated` |
| Authenticated but not allowed | 403 | `forbidden` |
| Resource doesn't exist | 404 | `not_found` |
| Method not allowed | 405 | `method_not_allowed` |
| State conflict (duplicate, idempotency-key reuse with a different body, invoice already paid) | 409 | `conflict` |
| Payload too large | 413 | `payload_too_large` |
| Rate limited (include `Retry-After`) | 429 | `rate_limited` |
| Unexpected server error (generic message, log details server-side) | 500 | `internal_error` |
| Upstream (payment processor) failure | 502 or 503 | `upstream_unavailable` |

**Why 422 for validation:** it cleanly separates "I couldn't parse this" (400) from "I understood it but it's invalid" (422). Both are already in use, so pick one rule and apply it everywhere. The alternative is to use 400 for everything, which is also defensible. What matters is that there is one rule. Business-rule rejections, such as refunding more than the charge, can also be 422 with a specific `code`, or 409 if they depend on current resource state.

**Never return 200 for a failure.** Clients, proxies, retry logic, and monitoring all key off the status.

The plan has a flaw: RFC 9110 says PUT and DELETE *should* be idempotent, but the spec can't make your server behave that way. Both endpoints you checked break the rule, so "retry every PUT and DELETE without a key" would cause duplicate writes.

## Endpoint audit

| Endpoint | Idempotent? | Why | Retry without a key? |
|---|---|---|---|
| `PUT /v1/accounts/{id}/notes` | No | It appends a new note on every call. If the response is lost and the SDK retries, the log gets duplicate notes. | **No** |
| `DELETE /v1/cart/items/{sku}` | No | It decrements the quantity by one. A retry after a lost response removes a second unit, or removes the line when the user wanted one fewer. | **No** |

RFC 9110 idempotency means N identical requests leave the same server state as one request. Neither endpoint meets that.

Both are the worst case for retries. A timeout or reset doesn't tell the client whether the first attempt ran, and a blind retry turns that uncertainty into silent data corruption. Nothing errors, so you'd find out from customer reports.

## Server changes

Pick one fix per endpoint, and fix the contract rather than the SDK.

**Notes (`PUT .../notes`)**
- Best option: make it a real PUT. Use a client-chosen note ID (`PUT /v1/accounts/{id}/notes/{note_id}`). Repeating the call with the same ID rewrites the same note, so it is idempotent by construction.
- Alternative: keep the append semantics but make it `POST /notes` with `Idempotency-Key` support. `POST` is the honest method for an append.
- Changing the method or path is a breaking change. Keep the old route, mark it deprecated, and don't give it automatic retries.

**Cart (`DELETE .../items/{sku}`)**
- Decrement-by-one is not a delete. Model it as one of these:
  - `PUT /v1/cart/items/{sku}` with `{"quantity": N}`, which sets an absolute state and is idempotent.
  - `POST /v1/cart/items/{sku}/decrement` with `Idempotency-Key`.
- Keep `DELETE` for "remove the line entirely", which is naturally idempotent. A repeat returns 204 or 404, and the SDK should treat both as success.

**Idempotency-key support, for any endpoint that stays non-idempotent**
- The client mints the key. The server never derives it from the payload.
- Scope it per account with a unique constraint on `(account_id, idempotency_key)`.
- Store a payload fingerprint with the key. The same key with a different body gets a distinct error (`422` or `409`), not a silent replay.
- Claim the key atomically, in the same transaction as the mutation. Don't check then insert.
- Track three states: absent, in-flight, and complete. For in-flight, return `409` with code `idempotency_request_in_progress`. For complete, replay the stored response verbatim.
- Set the replay window from your longest retry chain. 24 hours is a common default. Keep records longer than that, for example 72 hours.
- Decide whether a stored failure replays or can be re-attempted, and document the decision.
- `Idempotency-Key` is not a standard. The IETF draft expired, so you own the semantics. Document them.

## SDK retry policy

**What to retry**
- Retry automatically only on:
  - methods that are idempotent in behavior: GET, HEAD, and PUT/DELETE endpoints that your server team has verified, via an explicit per-operation allowlist
  - any operation that carries an idempotency key
- Don't decide by HTTP verb alone. Make each operation in the SDK's generated spec carry an `idempotent: true` flag. Default it to false.
- For unsafe operations, have the SDK generate a key once per logical call and reuse it on every attempt. A fresh key per attempt defeats the mechanism.

**When to retry**
- Retry on `408`, `429` (honor `Retry-After`), `502`, `503`, `504`, connection timeouts and resets, and `409 idempotency_request_in_progress` (same key).
- Treat `500` carefully, since many are deterministic bugs.
- Never retry other 4xx, auth failures, or the payload-mismatch error.

**How to retry**
- Use full-jitter exponential backoff: `sleep = random(0, min(cap, base * 2^attempt))`.
- Cap attempts at about 3, and set one overall deadline for the whole call. Don't reset the timeout on each attempt.
- Add a client-side retry budget. Stop retrying once retries exceed a share of traffic over a sliding window, so a fleet doesn't amplify an outage.
- Log every retry with the attempt number, the error, and the next wait.
- Default retries on, and document the defaults.

## Verification before shipping
1. **Concurrency test:** fire N identical requests with the same key at each state-changing endpoint. Exactly one side effect should happen, and the rest should get the in-flight conflict or the stored replay.
2. **Kill test:** drop the connection after the server commits but before the client reads the response. Retry, and confirm exactly one note is appended and one unit is removed.
3. **Audit the rest:** these two endpoints were the ones you happened to check. Check every other PUT and DELETE for the same append or decrement behavior before enabling the allowlist. Start with the allowlist empty and add endpoints as each is verified.

The plan is flawed. HTTP says PUT and DELETE are *intended* to be idempotent, but the spec can't make your server behave that way. Retry safety depends on what each endpoint does, not on its verb.

## Endpoint audit

**`PUT /v1/accounts/{id}/notes`: not safe to retry.**
- It appends a note on every call, so a retry after a timeout or lost response creates duplicate notes.
- This is a POST-style operation sent as PUT. It violates the PUT contract, which says repeating the request leaves the same server state as sending it once.

**`DELETE /v1/cart/items/{sku}`: not safe to retry.**
- Each call decrements the quantity by one. A retry after a lost response removes a second unit, so the customer loses an item they didn't ask to remove.
- Real DELETE semantics would remove the line, so repeating the call has the same effect as sending it once.

Both failures show up in the cases that matter most: timeouts, connection resets, and 502/503/504 responses. In those cases the client can't tell whether the server already applied the request.

## Server changes

You have two options for each endpoint. Pick one per endpoint.

1. **Make the endpoint match its verb.**
   - Notes: use `POST /v1/accounts/{id}/notes` for appends. If you need PUT, make it `PUT /v1/accounts/{id}/notes/{note_id}` with a client-generated ID, so a repeat overwrites the same note.
   - Cart: make `DELETE /v1/cart/items/{sku}` remove the whole line. Add `PATCH /v1/cart/items/{sku}` with an absolute `{"quantity": n}`, or a separate decrement endpoint that takes an idempotency key.
2. **Keep the behavior and support idempotency keys.**
   - Accept an `Idempotency-Key` header on every non-idempotent endpoint, including these two if you keep their current behavior.
   - Store the key, a hash of the request, and the response for a fixed window, such as 24 hours.
   - Replay the stored response when the same key and request arrive again. Return 409 or 422 if the key is reused with a different request body.
   - Make the key check and the write atomic, for example a unique constraint in the same transaction, so concurrent retries can't both apply.

Changing the semantics of existing routes is a breaking change. Version them or deprecate them rather than editing them in place.

Also audit every other PUT and DELETE before the SDK ships. These two were the only ones you checked, and they were both wrong.

## SDK retry policy

Don't key retries on the HTTP method. Key them on whether the request is known to be safe to repeat.

- **Always retry (with backoff):**
  - Failures that happen before the request is sent: connection refused and DNS failures.
  - 429 and 503 responses that include `Retry-After`. The server is explicitly saying it didn't process the request.
- **Retry only if safe:** timeouts, connection resets, and 500/502/504 responses. Retry these if either condition holds:
  - the request carries an idempotency key (SDK-generated, reused across all attempts of one logical call), or
  - the endpoint is explicitly marked idempotent in your API spec.
- **Never auto-retry:** POST, and any endpoint not marked idempotent, when there's no idempotency key.
- **Mechanics:**
  - Use exponential backoff with jitter and honor `Retry-After`.
  - Cap attempts and total elapsed time.
  - Generate the idempotency key once per logical call, not once per attempt.
  - Make retries configurable per call and per client.

The "marked idempotent" flag should be an explicit allowlist in the SDK, generated from the API spec and set after each endpoint is audited. That way a verb alone never decides, and an endpoint like these two can't be retried by accident.

# Review of the Redis SETNX lock, and the fix for the race

## Verdict on the SETNX proposal

Don't use it as the fix. It narrows the window without closing it, and it adds a new failure mode.

- **The lease can expire while the holder is still running.** If request A pauses (GC, slow DB, network stall) for more than 10 seconds, the lock expires and request B takes it. Both then create invoices. Without a fencing token, nothing stops A's late write.
- **Redis failover or loss loses the lock.** A failover, restart, or eviction drops it, and two requests run concurrently again.
- **Redis and Postgres can't commit together.** The lock and the invoice live in separate systems. Releasing the lock after a crash or timeout says nothing about whether the invoice exists.
- **It's a second system on the critical path.** If Redis is down you either fail every write or fail open, and failing open brings the race back.

The 30ms double-fire is a check-then-insert race, and Postgres can fix it on its own.

## Root cause

```
A: SELECT key  → none
B: SELECT key  → none
A: INSERT key; create invoice
B: INSERT key (no unique constraint, or error swallowed); create invoice
```

The SELECT can't pick a winner. Only an atomic operation in the storage layer can.

## The fix

**1. Add a unique constraint scoped per account.**

```sql
ALTER TABLE idempotency_keys
  ADD COLUMN request_fingerprint text NOT NULL,
  ADD COLUMN status text NOT NULL DEFAULT 'in_flight',  -- in_flight | complete
  ADD COLUMN response_status int,
  ADD COLUMN response_headers jsonb,
  ADD COLUMN response_body jsonb,
  ADD COLUMN locked_at timestamptz,
  ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();

CREATE UNIQUE INDEX CONCURRENTLY idx_idem_account_key
  ON idempotency_keys (account_id, key);
```

Before creating the index, dedupe any existing duplicates. If the current table has no unique index, that is the actual bug.

**2. Replace SELECT-then-INSERT with an atomic claim, in the same transaction as the invoice.**

```ruby
def create
  key  = request.headers["Idempotency-Key"] or return render_error(400)
  fp   = Digest::SHA256.hexdigest(request.raw_post)

  IdempotencyKey.transaction do
    claimed = IdempotencyKey.insert(
      { account_id: current_account.id, key: key, request_fingerprint: fp,
        status: "in_flight", locked_at: Time.current },
      unique_by: %i[account_id key]          # INSERT ... ON CONFLICT DO NOTHING RETURNING id
    ).rows.any?

    unless claimed
      # Lock the existing row. If the winner is still mid-transaction,
      # this blocks until it commits or rolls back.
      rec = IdempotencyKey.lock.find_by!(account_id: current_account.id, key: key)

      return render_error(422, "idempotency_key_reused") if rec.request_fingerprint != fp
      return replay(rec)                     if rec.status == "complete"
      return render_error(409, "idempotency_request_in_progress")
    end

    invoice = Invoice.create!(invoice_params.merge(account: current_account))
    # store the full response so a replay is identical
    IdempotencyKey.where(account_id: current_account.id, key: key).update_all(
      status: "complete", response_status: 201,
      response_headers: { "Location" => invoice_path(invoice) },
      response_body: InvoiceSerializer.new(invoice).as_json
    )
    render json: invoice, status: :created, location: invoice
  end
end
```

How it behaves under the 30ms double-fire:
- Postgres lets exactly one `INSERT` through. The other sees a conflict.
- The key row and the invoice commit together. If the invoice fails and the transaction rolls back, the key is released and the client can retry. This also fixes the inverse bug, where a key is recorded for an invoice that was never created.
- The loser blocks on the row lock until the winner commits. It then reads `complete` and replays the stored response, so the integrator gets the same `201` and invoice ID from both calls.

**3. Decisions to make and document**
- **Payload mismatch:** the same key with a different body returns a distinct error (`422 idempotency_key_reused`). Keep it separate from the in-flight `409`.
- **Stored failures:** decide whether a 4xx or 5xx replays verbatim or may be retried. With the transaction above, a rolled-back failure leaves no key, so it re-executes. If you want validation errors to replay, store them.

**Short answer:** don't use the Redis lock as the fix. The race comes from a missing database constraint, and the fix is to let Postgres arbitrate.

## Why SELECT-then-INSERT fails

Two requests 30ms apart both run the SELECT before either INSERT commits. Both see no row, both insert, and both create invoices. If the keys table has no unique index on the key, both inserts even succeed. If it does have one, the loser gets a constraint error that the controller probably doesn't handle, or the invoice is created outside the transaction. Check which case you're in, because it changes the migration.

## Why the Redis SETNX lock is the wrong fix

- **The TTL is a guess.** If a request outlives 10s (slow query, GC pause, deploy), the lock expires and a duplicate gets through. Redlock-style leases give no fencing guarantee.
- **The lock and the commit are separate.** If the lock is released before the DB transaction commits, a second request can read stale state and still duplicate.
- **Redis is a new failure mode.** On failover or an outage you must choose between failing open (duplicates return) and failing closed (the invoice endpoint goes down).
- **The invariant stays unenforced.** Retries from jobs, other endpoints, or a console session bypass the lock. Postgres is already your source of truth, so the guarantee should live there.

Redis can still serve as an optional optimization to reduce contention. It shouldn't be the thing that provides correctness.

## The fix

**1. Add a unique index.** Scope it to whatever the key's uniqueness scope is, typically the account.

```ruby
# dedupe existing rows first if any exist
class AddUniqueIndexToIdempotencyKeys < ActiveRecord::Migration[7.1]
  disable_ddl_transaction!
  def change
    add_index :idempotency_keys, [:account_id, :key],
              unique: true, algorithm: :concurrently,
              name: :idx_idempotency_keys_account_key
  end
end
```

**2. Insert first, in the same transaction as the invoice.** Use `INSERT ... ON CONFLICT DO NOTHING` instead of SELECT-then-INSERT.

```ruby
def create
  invoice = nil
  existing = nil

  ApplicationRecord.transaction do
    res = IdempotencyKey.insert(
      { account_id: current_account.id, key: idem_key, request_hash: request_hash },
      unique_by: :idx_idempotency_keys_account_key,
      returning: %w[id]
    )

    if res.rows.empty?
      existing = IdempotencyKey.find_by!(account_id: current_account.id, key: idem_key)
    else
      invoice = Invoice.create!(invoice_params.merge(account: current_account))
      IdempotencyKey.where(id: res.rows.first.first)
                    .update_all(invoice_id: invoice.id)
    end
  end

  if existing
    return render json: { error: "key reused with different payload" }, status: 422 if existing.request_hash != request_hash
    return render json: InvoiceSerializer.new(existing.invoice), status: :ok
  end

  render json: InvoiceSerializer.new(invoice), status: :created
end
```

**Why this closes the race:** when two transactions insert the same key, the second blocks on the first one's uncommitted index entry.

- If the first commits, the second's insert does nothing, and it returns the stored invoice.
- If the first rolls back, the second's insert succeeds and it proceeds.

Because the key and the invoice commit atomically, a crash can't leave a key with no invoice.

## Details to get right

- **Store a request fingerprint** (`request_hash`) so reusing a key with a different body returns 422 instead of silently returning the wrong invoice.
- **Set `lock_timeout` or `statement_timeout`** (for example 5s) so a blocked duplicate doesn't hold a connection indefinitely.
- **Keep slow external calls out of the transaction**, such as payment gateways or webhooks. If you need them, use a two-phase pattern instead: commit the key as `started` with a `locked_at`, do the work, then mark it `completed`. Concurrent duplicates get 409 while `started`.

**Don't use bcrypt. Store a SHA-256 hash of each key. Your reviewer's rule is right for passwords and wrong for this credential.**

**Why bcrypt is the wrong tool**
- Slow hashes exist to make guessing a low-entropy secret expensive. A random 32-byte key has 256 bits of entropy. No attacker can brute-force it at any hash speed, so a slow hash adds no security.
- It does add cost. bcrypt at a sane work factor takes about 50–100 ms of CPU per check. At 3,000 req/s that is roughly 150–300 cores spent only on authentication. Attackers can also use that cost against you by sending garbage keys.
- bcrypt truncates input at 72 bytes, and many implementations choke on NUL bytes. Both are bad properties for a binary-derived credential.
- You can't look up by bcrypt hash, because each hash has its own salt. You would need a separate lookup ID anyway.

**What the reviewer is actually protecting against**
The goal is that a database leak doesn't hand over usable credentials. Hashing the key achieves that. For 256-bit random inputs, SHA-256 is preimage-resistant, so the stored hash can't be reversed. You can say this to the reviewer directly: the bcrypt guidance is for human-chosen passwords, and the OWASP Password Storage Cheat Sheet is about those.

**Design**
1. **Format:** use `sk_live_<random body><checksum>`. Put the environment (live or test) in the prefix from the start. The body comes from a CSPRNG with at least 120 bits of entropy. Your 32 bytes is well above that. Show the key once at creation.
2. **Table:**
   ```sql
   CREATE TABLE api_keys (
     id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
     owner_id uuid NOT NULL,
     key_prefix text NOT NULL,   -- indexed lookup handle
     key_hash bytea NOT NULL,    -- SHA-256 of the full key
     name text NOT NULL,
     scopes text[] NOT NULL,     -- empty means no access
     created_at timestamptz NOT NULL DEFAULT now(),
     last_used_at timestamptz,
     expires_at timestamptz,
     revoked_at timestamptz
   );
   CREATE INDEX ON api_keys (key_prefix);
   ```
3. **Per request:**
   - Check the prefix, length and checksum. Reject malformed keys with no database call.
   - Fetch candidate rows by indexed `key_prefix`. Use the type and environment prefix plus a few body characters, or a separate random lookup ID embedded in the key. Count only the unstored part of the body toward the entropy floor. 32 random bytes leaves plenty.
   - Compute SHA-256 of the full key and compare with `key_hash` in constant time.
   - Check `expires_at` and `revoked_at`, then enforce scopes.
   - Update `last_used_at` asynchronously so it never blocks the request.
4. **At 3,000 req/s:** SHA-256 costs microseconds. Put a short-TTL in-process cache in front of the lookup, keyed by the hash, so the database is not hit on every request. Keep the TTL to seconds so revocation propagates quickly, or add explicit invalidation.

**Conditions that make this safe**
- Enforce the entropy floor at generation. If anyone can later choose their own key, SHA-256 is no longer enough.
- Fail closed. A missing secret, such as a KMS key, should stop the service at startup and never fall back to a default.
- Rate-limit validation failures and key creation like login endpoints.
- Return 401 for a bad key and 403 for a valid key without the scope.

**Operational items to add**
- Support rotation with two valid keys at once and a scheduled end for the old one.
- Track `last_used_at` so you can see when old keys go quiet.
- Give keys service-account or org owners, not individuals.
- Consider registering the key format with GitHub secret scanning.

## Refresh token policy

**Public clients (mobile and SPA): rotate on every use and detect reuse.** RFC 9700 requires public-client refresh tokens to be either sender-constrained or rotated. An unconstrained, reusable, never-expiring refresh token is the case the review flagged, and it isn't allowed.

- **Rotation:** Each refresh request returns a new access token and a new refresh token. The old refresh token is marked consumed.
- **Families:** Every refresh token belongs to a family that traces back to the original authorization grant. Store the family ID and the consumed or active state.
- **Lifetimes:**
  - Use an idle timeout, such as 30 days for mobile and shorter for SPAs. The timeout slides forward with each rotation.
  - Also use an absolute cap on the family, such as 90 days for mobile and days to a couple of weeks for SPAs. After the cap the user re-authenticates.
  - Browser storage is the most exposed, so SPAs get the tightest limits.
  - These numbers are starting points. Choose them from your own usage patterns.
- **Access tokens:** Keep them at about an hour or less. If they are JWTs, they can't be revoked mid-life, so keep them short.
- **Sender-constraining:** Offer DPoP (RFC 9449) or mTLS as an option, and make it the default where tokens guard financial or health data or long-lived agent access. Many client libraries don't support DPoP yet, so don't make it a baseline until you know your clients.
- **Revocation:** Keep user revocation of an app, which revokes the whole family. Add RFC 7009 `/revoke` so apps can revoke their own tokens on logout.

**Confidential clients:** Client authentication already constrains these. Non-rotating tokens with a per-client lifetime cap are defensible, but rotation is still the simpler default to apply everywhere.

## When a refresh token is presented a second time

**Revoke the whole family: every refresh token and the access tokens issued from them.** The server can't tell whether the attacker or the legitimate client presented the stale token. It only knows that the token was used twice, so it is safest to kill the active token too. RFC 9700 §4.14 describes this as a tripwire, not proof of theft. Log the event, and require re-authentication, since the user must sign in again.

**Add a short grace window, on the order of seconds, to avoid false positives.** Multi-tab SPAs, network retries, and a mobile app killed mid-response all re-present a token that was just consumed. Without a window these look like attacks and log out real users.

- Inside the window, return the **successor already issued** for that token. Make the refresh idempotent.
- Do **not** mint a second sibling token. A second child would let a replayed stolen token start a branch that reuse detection never sees.
- If you must re-issue, allow it once, then revoke the family on the next presentation.
- Outside the window, treat the presentation as reuse and revoke the family.
- Choose the window length from your own client behavior.

**Implementation notes**

- If you hash refresh tokens at rest, keep the predecessor's hash with a "consumed at" timestamp. Without it you can't recognize the just-consumed token during the grace window, or detect reuse after it.
- Make rotation atomic. Two concurrent refreshes must not both succeed. Use a conditional update on the token's state, or a transaction.
- Apply the same family revocation to authorization-code reuse. A code presented twice should revoke the tokens already issued from it.

## Rollout for existing tokens

Existing refresh tokens are long-lived and not in families. A reasonable migration is:

1. Ship rotation and family tracking. On an old token's next use, start a family and rotate it.
2. Apply the idle and absolute caps to migrated tokens, measured from migration time or from the original issue date, whichever you prefer.
3. For public clients, put a deadline on tokens that haven't been migrated, and force re-authorization after it.
4. Tell developers about the new `invalid_grant` behavior. Clients must store the new refresh token on every refresh and handle `invalid_grant` by sending the user back through sign-in.

## Recommended policy

**Public clients (mobile, SPA): rotate on every use, and revoke the whole grant if a token is reused.** This is what RFC 9700 (the OAuth Security BCP) and OAuth 2.1 require when refresh tokens aren't sender-constrained.

**Confidential clients:** these are authenticated with a client secret or key, so they have less exposure. You can use longer lifetimes and make rotation optional. Rotation is still a good default.

### Token lifetimes
- **Access tokens:** 5–15 minutes.
- **Refresh tokens, idle timeout:** 7–30 days for public clients. Each rotation resets it.
- **Refresh tokens, absolute lifetime:** 30–90 days from the original authorization, after which the user must re-authenticate. Pick the value based on your app's risk. A "valid until revoked" token should no longer exist for public clients.
- **Scope:** a refresh can keep or narrow the scope, never widen it.

### Rotation
- Every refresh request returns a new access token and a new refresh token. The old refresh token is immediately marked used.
- Keep all tokens from one authorization in a **token family** (a `family_id`, or a grant ID on every token). The family is the unit you revoke.
- Store only hashes of refresh tokens. Keep them opaque and high-entropy (at least 128 bits).

### When a used refresh token is presented again
A used token appearing again means either an attacker has a copy or the legitimate client lost the response. You can't tell which. The BCP-recommended response is:

1. **Reject the request** with `invalid_grant`.
2. **Revoke the entire family**: the current refresh token and the access tokens issued from it, where you can.
3. **Log and alert** with the client ID, user, IP and user agent of both the original and the replayed use, and the time gap.
4. **Force re-authentication.** The user logs in again, and the client gets a new family.

Without step 2, an attacker who steals a token and uses it first can keep refreshing, and the real user would simply be logged out. Revoking the family ends the attacker's session whichever of them replays first.

### Handling legitimate retries
Strict reuse detection will log out users whose network dropped the refresh response. There are two ways to reduce that:

- **Grace window:** allow the just-rotated token to be replayed for about 10–30 seconds. Return the same successor token, or a new one in the same family. Keep the window short and tied to the same client. Many providers do this, but it is a deliberate weakening, so make it configurable.
- **Client guidance:** tell client developers to serialize refresh calls. In an SPA, a single in-flight promise or a cross-tab lock prevents the most common cause of self-inflicted reuse, which is two tabs refreshing at once.

### Stronger option: sender-constrained tokens
Rotation detects theft after the fact. **DPoP (RFC 9449)** prevents a stolen token from being usable. The client holds a non-exportable key (WebCrypto in a SPA, Keystore or Secure Enclave on mobile) and binds the refresh token to it. If you can, support DPoP for public clients and require it for high-risk scopes. Rotation and DPoP work well together.

### Other controls
- Bind the refresh token to the `client_id`. Reject it from any other client.
- Require PKCE for all authorization code flows. It protects the initial grant, not the refresh.
- Let users see and revoke individual grants, and let admins revoke by user or client.
- Revoke families on password reset, on a security event, and on explicit logout.
- For SPAs, recommend a backend-for-frontend (BFF) where the refresh token never reaches browser JavaScript. That is stronger than anything done at the token layer.

### Migration
You already have long-lived tokens in the field.
1. Add the family model and rotation. Treat each existing token as the head of a new family.
2. Roll out rotation for public clients first, with metrics on reuse-detection hits before you enforce revocation.
3. Add the absolute lifetime and idle timeout. Apply them to existing tokens by capping their expiry at issuance date plus the absolute lifetime, with a deprecation notice period.
