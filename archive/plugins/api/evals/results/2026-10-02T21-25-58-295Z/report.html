## What's wrong

The app sends the key, but the handler doesn't use it safely. These are the problems, most serious first.

1. **Check-then-act race (`handler.py:11-35`).** The handler looks the key up, calls `processor.charge`, and only then inserts the key. On a flaky network the first request is often still running when the retry arrives, so the key row doesn't exist yet. Both requests see "absent" and both charge the card. This is the duplicate-charge bug.
2. **No uniqueness in the schema.** `idempotency_keys.key` has no `PRIMARY KEY` or `UNIQUE` constraint. Even if the handler claimed first, the database couldn't pick a single winner. The second `INSERT` would succeed and leave duplicate rows.
3. **The key isn't scoped to an account.** The lookup is `WHERE key = ?`. Two accounts that send the same key collide, and one account gets another account's stored response, including its `processor_ref`. The key should be unique on `(account_id, key)`.
4. **No in-flight state.** A key exists only after the charge has finished, so a retry arriving mid-charge has nothing to find. The key has to be claimed before the charge, with an "in progress" state.
5. **No payload fingerprint.** Reusing a key with a different amount silently replays the old response. This should be rejected.
6. **The card call isn't safe to repeat.** If the process crashes after the processor charges the card but before the commit, nothing is recorded. The retry then charges again. The processor call needs its own idempotency key derived from the client's key.
7. **Smaller issues.**
   - Replays always return `201`, and the stored status and headers are not kept.
   - The key is optional, so any client that omits it has no protection.
   - There is no cap on key length.
   - There is no expiry or cleanup.

## Corrected schema

```sql
CREATE TABLE charges (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id    TEXT NOT NULL,
  amount_cents  INTEGER NOT NULL,
  currency      TEXT NOT NULL,
  processor_ref TEXT NOT NULL
);

CREATE TABLE idempotency_keys (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id          TEXT NOT NULL,
  idempotency_key     TEXT NOT NULL,                -- client-minted, max 255 chars
  request_fingerprint TEXT NOT NULL,                -- sha256 of canonical payload
  locked_at           INTEGER NOT NULL,             -- epoch seconds; lock is live while response_status IS NULL
  lock_generation     INTEGER NOT NULL DEFAULT 0,   -- fencing token, bumped on takeover
  response_status     INTEGER,                      -- NULL = in flight
  response_body       TEXT,
  created_at          TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (account_id, idempotency_key)
);
```

## Corrected handler

```python
"""POST /v1/charges, called by integrators and by our own mobile app."""
import hashlib
import json
import time

import processor  # wrapper around the card processor's HTTP API

LOCK_TIMEOUT_S = 60  # must exceed the processor call's own timeout


def create_charge(db, account_id, headers, body):
    key = headers.get("Idempotency-Key")
    if not key or len(key) > 255:
        return 400, {"error": "idempotency_key_required"}

    fingerprint = hashlib.sha256(
        json.dumps(body, sort_keys=True, separators=(",", ":")).encode()
    ).hexdigest()
    now = int(time.time())

    # Atomic claim: the UNIQUE constraint picks exactly one winner.
    claimed = db.execute(
        "INSERT INTO idempotency_keys"
        " (account_id, idempotency_key, request_fingerprint, locked_at)"
        " VALUES (?, ?, ?, ?)"
        " ON CONFLICT (account_id, idempotency_key) DO NOTHING",
        (account_id, key, fingerprint, now),
    ).rowcount == 1
    db.commit()

    if claimed:
        generation = 0
    else:
        fp, status, resp, locked_at, gen = db.execute(
            "SELECT request_fingerprint, response_status, response_body,"
            " locked_at, lock_generation FROM idempotency_keys"
            " WHERE account_id = ? AND idempotency_key = ?",
            (account_id, key),
        ).fetchone()

        if fp != fingerprint:
            return 422, {"error": "idempotency_key_reused"}
        if status is not None:
            return status, json.loads(resp)  # replay verbatim, no re-execution
        if locked_at > now - LOCK_TIMEOUT_S:
            return 409, {"error": "idempotency_request_in_progress"}

        # Original executor died: take over, fenced by lock_generation.
        took_over = db.execute(
            "UPDATE idempotency_keys"
            " SET locked_at = ?, lock_generation = lock_generation + 1"
            " WHERE account_id = ? AND idempotency_key = ?"
            " AND response_status IS NULL AND lock_generation = ?",
            (now, account_id, key, gen),
        ).rowcount == 1
        db.commit()
        if not took_over:
            return 409, {"error": "idempotency_request_in_progress"}
        generation = gen + 1

    # Foreign call, made safe to repeat: the processor dedupes on this key,
    # so a takeover after a crash returns the original charge.
    ref = processor.charge(
        account_id=account_id,
        amount_cents=body["amount_cents"],
        currency=body["currency"],
        idempotency_key=f"{account_id}:{key}",
    )

    response = {"processor_ref": ref, "amount_cents": body["amount_cents"]}
    db.execute(
        "INSERT INTO charges (account_id, amount_cents, currency, processor_ref)"
        " VALUES (?, ?, ?, ?)",
        (account_id, body["amount_cents"], body["currency"], ref),
    )
    # Fenced completion in the same transaction as the charge row.
    finished = db.execute(
        "UPDATE idempotency_keys SET response_status = 201, response_body = ?"
        " WHERE account_id = ? AND idempotency_key = ?"
        " AND lock_generation = ? AND response_status IS NULL",
        (json.dumps(response), account_id, key, generation),
    ).rowcount == 1
    if not finished:  # we were superseded; commit nothing
        db.rollback()
        return 409, {"error": "idempotency_request_in_progress"}
    db.commit()
    return 201, response
```

## Required follow-ups

- **`processor.charge` needs an `idempotency_key` parameter.** The stub in `processor.py` doesn't have one. It must forward the value as the card processor's own idempotency header. Without it, a crash between the card call and the commit can still double-charge on takeover, so fix 6 isn't in place until this is done.
- **The key is now mandatory** on this endpoint (`400` if absent). Check that the mobile app and integrators always send it. The app must reuse one key across all retries of a single purchase and mint a new one for each new purchase.
- **Clients should retry `409 idempotency_request_in_progress`** with the same key. They should not retry `422`.
- **Migrating the existing table.** Old rows have no `account_id`, so you'll need a backfill or a fresh table.
- **Retention.** Add a job that deletes keys older than your longest retry chain, with about 24 hours as a floor and about 72 hours as a reasonable default.
- **Failures.** I left a processor exception unstored. The lock expires after 60 seconds and the next retry takes over, which is safe because of the processor-side key. If you'd rather store declined cards and replay them, add that explicitly.

## What's wrong

`create_charge` in `handler.py` checks for the key, charges the card, and only then records the key. Several problems follow from that.

1. **Check-then-act race (the main cause).** On a flaky network the app often retries while the first request is still waiting on the processor. Both requests run the `SELECT`, both miss, and both call `processor.charge`. The key isn't written until after the charge returns, so the window is the full processor round-trip.
2. **The schema can't enforce uniqueness.** `idempotency_keys.key` has no `PRIMARY KEY` or `UNIQUE`. Even if the handler were correct, the database would accept two rows for the same key.
3. **The charge and the key aren't recorded safely.** If the process dies after `processor.charge` succeeds but before `commit`, the money has moved and nothing is recorded. The retry then charges again. The processor is never told about the key, so it can't deduplicate either.
4. **Keys are global, not per account.** A key from one account can replay another account's stored response. Mobile keys are probably UUIDs, but integrators choose their own.
5. **The request body isn't checked.** Reusing a key with a different amount silently returns the old response instead of an error.
6. **Smaller issue.** There's no way to tell "in progress" from "done", so a concurrent retry has nothing sensible to return.

## Fix

The idea is to claim the key first, using a unique constraint as the lock. Commit that claim before touching the processor. Then charge, and record the charge and complete the key in one transaction.

### `schema.sql`

```sql
CREATE TABLE charges (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id    TEXT NOT NULL,
  amount_cents  INTEGER NOT NULL,
  currency      TEXT NOT NULL,
  processor_ref TEXT NOT NULL
);

CREATE TABLE idempotency_keys (
  account_id          TEXT NOT NULL,
  key                 TEXT NOT NULL,
  request_fingerprint TEXT NOT NULL,
  status              TEXT NOT NULL DEFAULT 'in_progress'
                        CHECK (status IN ('in_progress', 'completed')),
  response            TEXT,
  created_at          TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (account_id, key)
);
```

If this table already has data, dedupe it before adding the primary key. Existing rows have no fingerprint or status, so backfill those too.

### `handler.py`

```python
"""POST /v1/charges, called by integrators and by our own mobile app."""
import hashlib
import json

import processor  # wrapper around the card processor's HTTP API


def _fingerprint(body):
    canonical = json.dumps(
        {"amount_cents": body["amount_cents"], "currency": body["currency"]},
        sort_keys=True,
    )
    return hashlib.sha256(canonical.encode()).hexdigest()


def create_charge(db, account_id, headers, body):
    key = headers.get("Idempotency-Key")
    if not key:
        return _charge(db, account_id, body, key=None)

    fp = _fingerprint(body)

    # Claim the key. The primary key makes this atomic: exactly one concurrent
    # request gets rowcount == 1. Commit before calling the processor so that
    # retries arriving mid-charge see the claim.
    cur = db.execute(
        "INSERT INTO idempotency_keys (account_id, key, request_fingerprint)"
        " VALUES (?, ?, ?) ON CONFLICT (account_id, key) DO NOTHING",
        (account_id, key, fp),
    )
    claimed = cur.rowcount == 1
    db.commit()

    if not claimed:
        status, stored_fp, response = db.execute(
            "SELECT status, request_fingerprint, response FROM idempotency_keys"
            " WHERE account_id = ? AND key = ?",
            (account_id, key),
        ).fetchone()
        if stored_fp != fp:
            return 422, {"error": "Idempotency-Key reused with a different request"}
        if status != "completed":
            return 409, {"error": "original request still in progress, retry shortly"}
        return 201, json.loads(response)

    return _charge(db, account_id, body, key=key, fp=fp)


def _charge(db, account_id, body, key, fp=None):
    try:
        # Pass the key through so the processor dedupes if we crash or time out
        # after it has charged (requires processor.charge to accept it).
        ref = processor.charge(
            account_id=account_id,
            amount_cents=body["amount_cents"],
            currency=body["currency"],
            idempotency_key=f"{account_id}:{key}" if key else None,
        )
    except processor.CardDeclined:
        # Definite failure: release the claim so the client can retry.
        if key:
            db.execute(
                "DELETE FROM idempotency_keys WHERE account_id = ? AND key = ?",
                (account_id, key),
            )
            db.commit()
        raise
    # Any other exception (timeout, 5xx) is an unknown outcome: leave the claim
    # in_progress rather than risk a second charge.

    response = {"processor_ref": ref, "amount_cents": body["amount_cents"]}
    db.execute(
        "INSERT INTO charges (account_id, amount_cents, currency, processor_ref)"
        " VALUES (?, ?, ?, ?)",
        (account_id, body["amount_cents"], body["currency"], ref),
    )
    if key:
        db.execute(
            "UPDATE idempotency_keys SET status = 'completed', response = ?"
            " WHERE account_id = ? AND key = ?",
            (json.dumps(response), account_id, key),
        )
    db.commit()  # charge row and completed key land together
    return 201, response
```

## Things to check or decide

- **I haven't run this.** `processor.py` is a stub, so I couldn't test it.
- **Processor changes it assumes.** `processor.charge` needs an `idempotency_key` parameter, passed through to the card processor's own idempotency header. It also needs a `CardDeclined` exception for definite failures. Both are assumptions about the real wrapper.
- **Stuck `in_progress` claims.** After a timeout or crash, the claim stays `in_progress` and retries get 409 indefinitely. Add a staleness rule: if the claim is older than the processor timeout, allow a retake. That's safe because the processor dedupes on the key. Alternatively, run a reconciliation job.
- **Existing duplicates.** The fix prevents new duplicate charges. Support will still need to find and refund the ones already created.
- **Other databases.** The `ON CONFLICT DO NOTHING` syntax works on SQLite and Postgres. On MySQL, use `INSERT IGNORE`.
