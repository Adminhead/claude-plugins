**Blocking for a public push**

**No-go.** Don't apply this plan.

**Why**

The PR changes `identifier` on `aws_db_instance.orders` from `orders-prod` to `orders-production` (`plan.txt:18`, `main.tf:2`). In the AWS provider, that change forces replacement, and `moved` blocks don't help. A `moved` block fixes Terraform addresses, but the RDS identifier is a real attribute of the instance. The plan shows `-/+ destroy and then create replacement` for the production orders database.

Applying it would do the following:
- **Data loss:** `skip_final_snapshot = true` means no final snapshot is taken when the old instance is destroyed. The 500 GB of data would be gone, and the replacement would be an empty database.
- **No safety net:** `deletion_protection = false` means nothing blocks the destroy.
- **New endpoint:** `endpoint`, `arn` and `id` are all "known after apply". Anything pointing at `orders-prod.example...` would break.

The security group change is harmless: it adds ingress `10.20.0.0/16`. It isn't part of a naming cleanup, though, so ask the author whether it's intentional.

**What the PR should do instead**

1. **Revert the identifier.** Set `identifier = "orders-prod"` in `main.tf` and keep the rest of the cleanup. The plan should then show no change on the database. The identifier is the real RDS name, so the tidy-up has to leave it alone. Rename only the Terraform resource label if you want a different name there, and pair that with a `moved` block. The plan should say "has moved to" with no destroy.
2. **If the new name is a hard requirement,** treat it as a migration, not a tidy-up. RDS can rename an instance in place (`modify-db-instance --new-db-instance-identifier`), but that still changes the endpoint. Plan it as a separate change with a maintenance window and a snapshot first. Then sync Terraform with the new name, using `terraform plan` to confirm it shows no replacement. Note that Terraform's `apply_immediately` and in-place rename behaviour depend on the provider version, so check the plan output either way.
3. **Add guardrails** whatever you decide:
   - `deletion_protection = true`
   - `skip_final_snapshot = false` plus a `final_snapshot_identifier`
   - `lifecycle { prevent_destroy = true }` on the database
4. **Split the security group change** into its own PR, or confirm it's intended.
5. **Re-plan and re-review.** The new plan should show no `-/+` on the database before anyone applies it.
