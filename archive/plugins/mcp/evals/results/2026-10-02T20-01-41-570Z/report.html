Your CI only checks the schema. What an agent chooses from is the tool's name, description, toolset grouping and schema together, and the model reads all of them. A reworded description or a renamed toolset can change which tool gets picked without touching the schema.

## Treat the whole surface as the contract

Three layers change at different speeds, so version them separately.

1. **Protocol revision.** Pin exact SDK versions and read the release notes before upgrading. This layer is negotiated, so it isn't what bit you.
2. **Public tool API.** Renaming or removing a tool, or moving it between toolsets, is a breaking change because agents find tools by name. Keep the old name as an alias, and publish a deprecation window. Your toolset rename should have gone through this process.
3. **Names, descriptions and schemas.** No spec covers this layer. Treat a description edit as a breaking change, because it can change tool selection even when the schema is identical.

## CI changes

- **Hash the full surface, not just the schemas.** Snapshot every tool's name, description, annotations, input and output schemas, and toolset membership into one golden file that is checked in. Any diff fails CI until someone updates the snapshot deliberately. This turns a silent wording change into a visible diff in the PR.
- **Run golden prompts.** Keep a fixed set of prompts, such as "find orders for customer X from last week" and "cancel this order". Each is paired with the tool it must select. Run them against a real model on every PR that touches the snapshot. Include near-miss cases between sibling tools. `search_orders` against `list_orders` or `get_order` is exactly where a reworded description causes mix-ups. Track the selection rate rather than a single pass or fail, since model output is noisy.
- **Classify changes mechanically.** A script that diffs the snapshot can label each change: *rename or removal* (breaking), *description or toolset change* (behavioral, needs golden-prompt evidence), *new optional parameter* (additive), and so on. Print the label in the PR.

## Review process

- Add a CODEOWNERS entry for the snapshot file and the tool definitions, so a tool-surface owner has to approve. Copy editing isn't a reason to skip this.
- Use a PR template with questions like these:
  - Did any names, descriptions or toolsets change?
  - Which golden prompts cover the change?
  - Is there an alias or a deprecation note?
- Write descriptions for tool selection, not as documentation. Each one should say when to use the tool, what it returns, which parameters are required, and how it differs from its nearest sibling. "Clearer" prose that drops the sibling distinction is a regression.
- Keep a changelog of the tool surface and bump a surface version, such as semver, on each change. Breaking means rename, removal, or a selection regression. Minor means additive. Patch means a wording change with golden prompts unchanged.

## Rollout

- Ship description and toolset changes behind a flag or to a canary, and compare tool-call distributions and error rates against the baseline before going wide. Tool-call telemetry is the only way to catch what golden prompts miss.
- Log which tool names get called and which calls fail with unknown or invalid tools. A spike after a deploy is your alarm.
- Keep rollback simple: the surface should be one versioned artifact you can revert.

## Related design points

- Keep the surface to roughly 5 to 15 tools. Toolset switching and dynamic loading make the surface harder to snapshot and test, so use them only when you have a breadth need you can demonstrate.
- Generate tools from your stable API contract where you can, so the two don't drift apart.

**No, it isn't enough.** Product's position treats the client dialog as a security control, and the MCP spec says it isn't one.

**Why it fails**
- **Annotations are hints.** The spec requires clients to treat annotations as untrusted unless the server is trusted. `destructiveHint` tells a client how to behave, and nothing enforces it.
- **The dialog is outside your control.** Some clients auto-approve. Users pick "always allow". Headless and unattended agents have nobody to click. Someone can also switch to a client with no prompt at all. A confirmation you don't enforce doesn't count as a confirmation.
- **Dialogs are weak even when they appear.** A prompt-injected agent can issue a plausible-looking `send_payment`, and users who see many prompts click through them.
- **The tiers are different.** Sending a customer message is a contained write. `send_payment` moves money, which is critical tier. Critical tools should be disabled by default and, if enabled, gated on every call. They should also have a spend cap and a dry-run.

**What to change in the server**

1. **Scoped credentials.** Give the server an upstream credential limited to the operations it needs, not a full-power key. Use a sandbox or test-mode account where one exists. It's the cheapest fix, so ship it first.
2. **Server-side approval on every call to both tools.** Use the protocol's input-required round trip (or elicitation on legacy connections). Show the real amount, payee, message body and recipient, taken from the server's own data rather than model text. Log the decision.
3. **Two-phase flow with dry-run.** Add `dry_run: true`, or split each tool into a preview step and a commit step. The preview returns exactly what would be sent or paid and changes nothing. The commit takes a short-lived, single-use token bound to those exact arguments, so the model can't preview one thing and commit another.
4. **Idempotency keys, required on both tools.** A retried call must not pay or message twice.
5. **Caps enforced per credential or user.**
   - Payments: a per-payment limit, a daily total, and an allow-list or known-payee check. Anything above the limit needs out-of-band approval.
   - Messages: rate and volume limits, plus recipient validation (the customer must belong to the caller's scope).
6. **Disabled by default, plus read-only mode.** Make `send_payment` opt-in per deployment. Add a server flag that removes write tools from `tools/list` and rejects the calls. Test that the tools are actually absent, because a flag that is set but not honored is the common failure.
7. **Authorization and attribution.**
   - Act as the calling user, with scopes checked per tool. Return 403 `insufficient_scope` otherwise.
   - On remote HTTP, validate the token audience and never pass the caller's token through to upstream.
   - Write an audit log with identity, tool, redacted arguments, approval result and outcome.
8. **Treat tool output as untrusted input to the model.** Keep descriptions static. Don't echo customer-supplied text back as if it were instructions.

Keep the annotations and set them honestly. `destructiveHint` and `openWorldHint` are right for both tools, and they're still worth having for supervised users. Just describe them to product as a UX nicety rather than the safeguard.

**Suggested order:** 1 → 6 (default-off payments) → 2 and 4 → 5 → 3 → 7. Messages can ship earlier with approval, an idempotency key and a rate cap. Payments should wait for approval, caps and dry-run.

**Why it fails**
- The MCP spec says clients *should* prompt, but nothing makes them. Annotations are untrusted hints from the client's point of view, and a client can ignore them.
- Many clients offer "always allow", auto-approve modes, or headless and scheduled agent runs with no human present. Your server can't tell which case it is in.
- A user who sees a dialog dozens of times a day stops reading it. The risky case is prompt injection, where text in a customer message or ticket steers the model into calling `send_payment`. The dialog is then the only defense, and it shows model-written arguments.
- Other clients, scripts, or a compromised token can call your server directly and skip any client-side dialog.

If product's position is "the client handles it", then nothing on your side stops a payment when the client doesn't.

**What to change in the server**
1. **Enforce authorization server-side.**
   - Authenticate every call.
   - Give these two tools their own OAuth scopes (e.g. `payments:send`, `messages:send`), so a token that can read data can't spend money or message customers.
   - Check that the caller may act on that specific account or customer.
2. **Require approval that the server verifies.**
   - Use a two-phase flow. The tool creates a pending action and returns a preview with an action ID. Execution happens only after an approval the server verifies.
   - For payments, approval should come out-of-band, such as your own UI, a push notification, or a signed link. If the model can call the confirm step itself, it isn't a real gate.
   - MCP elicitation is a reasonable middle ground. The server asks the user directly through the client. Fail closed if the client doesn't declare the capability. It's still client-mediated, so for high-value payments use the out-of-band route.
3. **Add hard limits that don't depend on approval.**
   - Per-payment and daily amount caps, with step-up approval above a threshold.
   - Recipient or payee allowlists.
   - Rate limits and velocity checks on both tools.
   - For customer messages, restrict recipients to the authenticated account's customers and consider templates or content checks.
4. **Make the tools idempotent.** Require an idempotency key so retries or duplicate model calls can't pay or message twice.
5. **Validate every input server-side.** Treat arguments as untrusted: amounts, currency, destination, and recipient.
6. **Write an audit log** with the principal, client, arguments, approval evidence, and result. You'll want it for incident review.
7. **Keep the annotations, but only as hints.** Make sure `readOnlyHint: false` and `destructiveHint: true` are set, and add `openWorldHint: true` on `send_customer_message`. `idempotentHint` should be true only if you actually implement idempotency keys.

For priority, I'd do 1, 3, and 4 first because they're cheap and independent of the client. Then do 2 for payments.

## Must change before launch

**1. Stop forwarding the client's bearer token (critical, confused deputy).**
- The spec says an MCP server must accept only tokens issued for it as the audience. It must not pass through any other tokens.
- Forwarding means the internal API trusts whatever token a customer presents. Any token that API accepts works against your MCP server, and the reverse.
- It also means the MCP server cannot enforce scopes or tenancy itself.
- **Inbound:** validate every request on every route. Check the signature, issuer, expiry, and `aud` equal to your MCP server's canonical URI (RFC 8707).
- **Outbound:** call the internal API with your own credential. Use OAuth token exchange (RFC 8693) to mint a short-lived, narrowly scoped token for the user. If you can't, use a service credential plus a verified user and tenant identity passed in a signed form the API checks. A bare "on-behalf-of" header is not enough.
- Never send the inbound `Authorization` header upstream. Add a test that fails if it appears in outbound calls.

**2. Publish proper OAuth resource-server behavior.**
- Serve protected resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource`.
- Return 401 with a `WWW-Authenticate` header pointing to that metadata for missing or invalid tokens. Return 403 for insufficient scope.
- Leave only the metadata route unauthenticated.
- Use a real authorization server. If it isn't built yet, `api:oauth-provider` covers that.
- Separate read, write, and admin scopes, and enforce them per tool on the server. Tool annotations are advisory and must not gate access.

**3. Remove the dependence on sticky sessions.**
- First decide which protocol revisions you serve. Under 2026-07-28 there are no protocol sessions or `initialize` handshake, so a server serving only that revision needs no session state.
- If you support older revisions, a session ID must never act as authentication. Generate IDs with a CSPRNG, bind them to the authenticated principal, and re-check the token on every request. A stolen or replayed ID must grant nothing.
- Move any state that has to survive across requests into a shared store such as Redis or a database, keyed by tenant and user. Then any instance can serve any request. Test by killing an instance mid-conversation.
- For handles that stateful tools return, check authorization against the handle on every call.
- Streamable HTTP's optional server-initiated streams and resumption also need a shared store (event log) or must be dropped.

**4. Add rate limiting in the server itself.**
- The spec requires it. A gateway alone is not enough.
- Key limits by authenticated identity or tenant, and use tighter budgets for write and expensive tools. Cover discovery calls too.
- Return 429 with `Retry-After` before any backend call.
- With multiple instances, the counters need a shared store, or you need a per-instance budget that accounts for the instance count.
- Set the budgets from your internal API's capacity.

**5. Validate input on every call.**
- Give each tool an explicit schema with types, bounds, enums, required fields, and closed properties.
- Invalid input should fail before any backend call.
- Errors should not leak stack traces, internal hostnames, or upstream response bodies.
- Check any tool that takes a URL, path, or free-form query for SSRF, path traversal, and injection into REST paths. Encode path parameters rather than concatenating them.

**6. Add transport hardening.**
- Validate `Origin` on all HTTP connections and return 403 for a bad one. Many SDK handlers don't do this by default.
- Terminate TLS, and set CORS to an explicit allowlist.
- Cap request size and apply timeouts.
- Check that the `MCP-Protocol-Version` header and the other routing headers agree with the request body.
- Don't put sensitive parameters in headers.

**7. Add audit logging and tenant isolation.**
- Log every tool call with caller identity, tenant, tool, time, and outcome. Redact tokens and arguments that hold secrets, and send logs to central storage.
- Keep no cache, state, or response data shared across tenants.
- Return minimal data, and treat upstream content returned to the model as untrusted data.

## Must change before launch

**1. Stop forwarding client bearer tokens to the internal API (token passthrough).**
- The MCP authorization spec explicitly forbids this. The server must only accept tokens issued for itself, and it must not pass them through to downstream APIs.
- Today the internal REST API is effectively exposed to the internet, with the MCP server as a dumb proxy. Any token the client presents is trusted downstream, and the API can't tell a token minted for it from one minted for something else.
- Audience confusion and replay become possible. A token stolen from any service that shares your issuer could be replayed through the MCP server.
- Audit logs, rate limits and attribution on the internal API will see the MCP server, not the real caller.
- **Fix:**
  - The MCP server validates the token as a resource server: signature, `iss`, `exp`, and `aud` equal to the MCP server's canonical URI (RFC 8707 resource indicators).
  - It then calls the internal API with its own credential. Use OAuth token exchange (RFC 8693) or a service identity (mTLS or workload identity) with the user's identity and scopes carried as a signed claim.
  - The internal API should enforce authorization against that exchanged identity, not just trust the MCP server.

**2. Implement the MCP authorization flow properly.**
- Act as an OAuth 2.1 resource server.
- Publish Protected Resource Metadata (RFC 9728) at `/.well-known/oauth-protected-resource`.
- Return `401` with a `WWW-Authenticate` header pointing at that metadata.
- Require PKCE, and support Client ID Metadata Documents or Dynamic Client Registration.
- Enforce per-tool scopes. Return `403` with `insufficient_scope` when a scope is missing.
- Use a real authorization server (your IdP) and don't build your own.
- Tokens must be short-lived, with refresh handled by the client. Never accept tokens in query strings.

**3. Replace sticky-session state with a stateless or externalized design.**
- Sticky sessions mean a deploy, crash or autoscale event drops sessions. They also cause hot instances and make failover painful.
- Prefer the stateless Streamable HTTP mode: no server-side session required per request, and each request is self-contained.
- If you need state (subscriptions, long-running tasks, resumable streams), put it in Redis or a database. Key it by session ID plus authenticated principal.
- **Session IDs are not authentication.** Generate them with a CSPRNG and bind each one to the user and token's `sub`. Re-verify the token on every request, and reject a session ID presented by a different principal. This prevents session hijacking and event injection.
- Any instance must be able to serve any request. For SSE resumption, store events externally (`Last-Event-ID`).

**4. Multi-tenant isolation.** Every tool call, resource and cache entry must be scoped by tenant and user derived from the validated token, never from request arguments. Confirm that no module-level or global state, left over from the stdio single-user model, leaks between customers.

**5. Transport hardening for a public endpoint.**
- Require TLS, and validate the `Origin` header on all requests to defend against DNS rebinding and browser-based attacks. Use a strict CORS allowlist.
- Don't bind to `0.0.0.0` without a gateway or WAF in front.
- Enforce request size limits, timeouts, per-tenant and per-token rate limits and concurrency caps, and cap SSE stream duration and count.

**6. Treat tool inputs, and tool outputs, as untrusted.**
- stdio assumed a trusted local user. Now arguments come from arbitrary clients, so validate them against schemas server-side and don't build internal API paths or queries by string concatenation (SSRF, path traversal, injection).
- Tool results that include customer-controlled data are a prompt-injection vector against your customers' LLMs. Keep tool descriptions static and versioned, and don't return secrets or internal error details.
- Mark destructive tools clearly, and require confirmation or narrow scopes for them.

**7. Secrets and error handling.** Never log `Authorization` headers or tokens. Redact them in access logs, traces and error reports. Map internal API errors to sanitized MCP errors.

## Should have for production
- **Observability:** per-tenant metrics, structured audit logs (who called which tool, with what scope), and request and trace IDs propagated to the internal API.
- **Operations:** health and readiness endpoints, graceful shutdown that drains SSE streams, and a deploy strategy that tolerates reconnects.
- **Abuse controls:** quotas, a kill switch per tenant, and token revocation handling. Use short TTLs or introspection for high-risk scopes.
- **Testing:** conformance tests for auth failure paths (wrong audience, expired, replayed session ID from another user), plus load tests that include instance restarts mid-session.
- **Supply chain and compliance:** dependency pinning and scanning, a security review or pen test, and a documented data-retention policy for logged tool payloads.

1. Token validation plus a downstream credential (items 1 and 2). This is the blocker, because it determines the trust model.
2. Externalize or remove session state (item 3).
3. Tenant isolation and input validation (items 4 and 6).
4. Transport limits and observability (items 5 and 7).

## What to change

1. **Cut to about 10–20 task-level tools.**
   - Group by user intent, not endpoint. For example, `find_invoices(customer, status, date_range)` replaces list, search, and get-by-customer. `get_invoice(id)` stays separate.
   - Merge the CRUD variants with a small action or enum parameter only where the semantics really are the same.
   - Drop endpoints no customer agent needs: admin, internal, and deprecated ones.

2. **Split read and write, and flag the risk.**
   - Set the MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`) so clients can auto-approve reads and gate writes.
   - Consider shipping a read-only server profile or scope by default. Customers can then opt into writes.

3. **Rewrite the descriptions by hand.**
   - Say when to use the tool and when not to ("Use for lookup by customer or status. For a known invoice ID, use `get_invoice`").
   - Document parameter formats with examples.
   - Say what comes back.

4. **Make responses agent-sized.**
   - Return the useful fields, not the whole object, and add a `detail`/`fields` option for more.
   - Use sensible default limits and tell the agent when results are truncated, for example "showing 20 of 143, narrow with `status`".

5. **Write actionable errors.** Instead of `400 Bad Request`, return something like "`date_range.end` must be after `start`; format is YYYY-MM-DD". Opaque errors are a major cause of retry loops.

7. **Consider a code-execution or search-tools layer if you really need breadth.** If customers need the long tail of endpoints, expose a few core tools plus a `search_api` and `call_api` pair. That's better than 74 always-loaded definitions.
