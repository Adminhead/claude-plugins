# Security Hardening

Config keys and commands checked against ESP-IDF v6.0 docs. The esptool tools use hyphenated subcommands from esptool v5 (`espsecure generate-signing-key`, `espefuse burn-efuse`). Older installs use `espsecure.py` and underscores, so check `--help` on the installed version.

## Confirm before flashing or burning anything

eFuse writes cannot be undone, and flashing a build that enables a security option performs them: the bootloader burns the eFuses on first boot. That includes development-mode flash encryption, which writes a key block and, unless `CONFIG_SECURE_BOOT_ALLOW_JTAG` is set, `DIS_PAD_JTAG`, `DIS_USB_JTAG`, `DIS_DOWNLOAD_ICACHE`, and `DIS_DIRECT_BOOT`.

Before any flash, check the resolved `sdkconfig` for `CONFIG_SECURE_BOOT*`, `CONFIG_SECURE_FLASH_ENC_ENABLED`, `CONFIG_SECURE_DISABLE_ROM_DL_MODE`, `CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK`, a changed `CONFIG_BOOTLOADER_APP_SECURE_VERSION`, and `CONFIG_NVS_SEC_KEY_PROTECT_USING_HMAC`. If any is set, get explicit confirmation that names the port and lists each permanent effect. Test the whole flow on a sacrificial board first.

Production signing and encryption keys are generated by the user under their own key management (offline machine, HSM, or a signing service). Do not generate, hold, or paste production keys yourself. Key paths below are placeholders.

| Feature | Configured by | Reversible? | Production? |
| --- | --- | --- | --- |
| Secure Boot v2 | eFuse + sdkconfig | No | Yes, for signed field devices |
| Flash encryption, development mode | eFuse + sdkconfig | No. Key and JTAG/download eFuses burn on first boot; ROM download can still write plaintext | Engineering builds only |
| Flash encryption, release mode | eFuse + sdkconfig | No | Yes, for sensitive data |
| NVS encryption | sdkconfig + key scheme | Flash-encryption scheme: key partition can be erased. HMAC scheme: burns an eFuse key block | If NVS holds secrets |
| JTAG disable | eFuse | Permanent (a soft-disable path exists) | Yes |
| UART ROM download disable | eFuse | No | Yes, with the above |
| Anti-rollback secure version | eFuse | No; the version only goes up | If downgrade is a threat |
| Console auth or removal | app code | Yes | Yes, if a console ships |

## Secure Boot v2

Signs the bootloader and app. Key settings:

```
CONFIG_SECURE_BOOT=y
CONFIG_SECURE_BOOT_V2_ENABLED=y
CONFIG_SECURE_BOOT_BUILD_SIGNED_BINARIES=y
CONFIG_SECURE_BOOT_SIGNING_KEY="<absolute path outside the repo>"
```

- The scheme and key count depend on the chip. Classic ESP32 (revision 3 and later) holds one RSA-3072 digest. S2, S3, C3, and C6 can hold up to three. ECDSA is available only on chips with ECC secure-boot support (C2, C6, H2, and others). Follow your chip's Secure Boot v2 guide.
- The user generates the key: `espsecure generate-signing-key --version 2 --scheme rsa3072 <path>` (or `--scheme ecdsa256` where supported). Keep it off the project tree, and use external or HSM signing where the process allows. A leaked signing key ends the protection.
- Sign a binary by hand with `espsecure sign-data --version 2 --keyfile <key> --output <signed.bin> <in.bin>`. Only the bootloader and app images need signing.
- The key digest goes into an eFuse key block and `SECURE_BOOT_EN` is burned, by the bootloader on first boot or by hand with `espefuse burn-key` and `burn-efuse`.
- With `CONFIG_SECURE_BOOT_ENABLE_AGGRESSIVE_KEY_REVOKE`, a failed verification revokes a key digest for good, and revoking all keys bricks the device. Leave it off unless the threat model asks for it.
- Without Secure Boot, anti-rollback and signed-app checks stop network attackers only. Someone with serial access can still replace the bootloader and bypass them.

## Flash encryption

Keys: `CONFIG_SECURE_FLASH_ENC_ENABLED`, with `CONFIG_SECURE_FLASH_ENCRYPTION_MODE_DEVELOPMENT` or `CONFIG_SECURE_FLASH_ENCRYPTION_MODE_RELEASE`.

- Development mode lets ROM download mode encrypt plaintext internally, so an attacker can write chosen plaintext. It is not secure, and it is not undoable. Use `idf.py encrypted-flash` to re-flash while it is active.
- Release mode locks that path. Use it for production and manufacturing.
- Prefer a per-device key generated on the device at first boot. A key shared across a fleet means one extraction exposes every unit. If a factory process must inject keys, the user generates them (`espsecure generate-flash-encryption-key <path outside the repo>`), burns them with `espefuse burn-key`, and keeps the file under their key management.
- Enabling flash encryption or Secure Boot makes the bootloader permanently disable JTAG on first boot, unless `CONFIG_SECURE_BOOT_ALLOW_JTAG` is set. That option is for testing only, because it negates flash encryption.
- SPIFFS partitions cannot be flash-encrypted. Keep secrets in encrypted NVS or another encrypted data partition.

## UART download and JTAG

- `CONFIG_SECURE_UART_ROM_DL_MODE` selects what happens to ROM download mode. `CONFIG_SECURE_DISABLE_ROM_DL_MODE` burns an eFuse that disables it for good, which also blocks esptool and espefuse, so you can no longer recover by serial.
- eFuses such as `DIS_PAD_JTAG` and `DIS_USB_JTAG` can be burned by hand. The Secure Boot and flash-encryption defaults already cover JTAG.
- Run `espefuse summary` before shipping and look for unexpected bits.

## NVS encryption

`CONFIG_NVS_ENCRYPTION` encrypts an NVS partition with XTS-AES. Keys are protected either by flash encryption (needs an `nvs_keys` partition; `CONFIG_NVS_SEC_KEY_PROTECT_USING_FLASH_ENC`) or derived from an HMAC key in eFuse (`CONFIG_NVS_SEC_KEY_PROTECT_USING_HMAC`, a permanent key-block burn that follows the confirmation gate above).

- The `nvs_keys` partition must carry the `encrypted` flag so flash encryption protects the keys. See [templates/partitions/ota_16mb.csv](../templates/partitions/ota_16mb.csv).
- With the option on, `nvs_flash_init()` already handles the default `nvs` partition. Any additional NVS partition needs `nvs_flash_secure_init_partition(label, cfg)` with its own key configuration.
- For explicit HMAC-scheme control, fill `nvs_sec_config_hmac_t`, call `nvs_sec_provider_register_hmac()`, then `nvs_flash_read_security_cfg_v2()` (generating keys with `nvs_flash_generate_keys_v2()` when the key is absent) and `nvs_flash_secure_init()`. Read the NVS encryption page for the exact sequence on your IDF version.

## Service console

Remove the console from production builds with a Kconfig flag, or require authentication before sensitive commands. Compare secrets in constant time, rate-limit failures, never print stored secrets, and drop destructive commands. See [console](device-terminal-console.md).

## Other build settings

- `CONFIG_COMPILER_STACK_CHECK_MODE` enables stack canaries (Normal or Strong). Avoid "Overall", which is large.
- `CONFIG_HEAP_CORRUPTION_DETECTION` selects `CONFIG_HEAP_POISONING_DISABLED`, `_LIGHT`, or `_COMPREHENSIVE`. Raise it temporarily in test builds to find out-of-bounds writes.
- `CONFIG_COMPILER_OPTIMIZATION_ASSERTION_LEVEL` is a choice of `ASSERTIONS_ENABLE`, `ASSERTIONS_SILENT`, or `ASSERTIONS_DISABLE`. Silent saves code size and keeps abort behavior.
- Pin or verify TLS server identity for OTA and cloud links. The certificate bundle trusts public CAs. `cert_pem` sets the trust anchor (for example your CA certificate), so it limits trust to that anchor but does not pin a leaf certificate.
- Zero key material after use with `explicit_bzero()`. Never log credentials or tokens.

## Production checklist

- Signing and encryption keys were generated by the user, are stored outside the repo, and are backed up. Flash-encryption keys are per device where possible.
- Secure Boot v2 and flash encryption (release mode) are on, and tested on a development unit first.
- NVS encryption covers every partition that holds secrets, and the `nvs_keys` partition is encrypted.
- JTAG and UART download are locked down by the chosen policy.
- OTA images are signed (Secure Boot, or signed-update verification at minimum), served over verified TLS, and anti-rollback is set deliberately.
- The console is removed or auth-gated.
- `CONFIG_ESP_HTTPS_OTA_ALLOW_HTTP` is off, and no verbose logging leaks data.
- `espefuse summary` was reviewed before shipping.
