# Nullable reference types

Adapted from the upstream `migrate-nullable-references` skill and its references (dotnet/skills); the PowerShell readiness scanner was not ported.

## Migration rules

- A migration is annotations only: `?`, `!`, nullable attributes and `#nullable` directives. These don't change IL. If you find a missing null guard or a real bug, don't fix it in the migration; offer a `// TODO: consider ArgumentNullException.ThrowIfNull(param)` and fix it in a separate change.
- `?` on a value type (`int?`, an enum, a struct) is not an annotation: it changes the type to `Nullable<T>`, the signature and boxing. Only add it to value types on purpose.
- Keep existing `ArgumentNullException` checks; callers without nullable, other languages, reflection or `!` can still pass null.
- Decide each member's intended nullability first, then annotate. Don't let warnings drive annotations (blanket `?` pushes null checks onto every caller; blanket `!` hides bugs). Ask the user before changing a public API's nullability when intent isn't clear from code or docs.
- Commit at each step boundary so each diff stays reviewable.

## Rollout

Requires C# 8+. A .NET Framework project defaults to C# 7.3; raising `LangVersion` is the user's call.

| Size | Strategy |
| --- | --- |
| Small to medium (roughly under 50 files) | `<Nullable>enable</Nullable>`, fix everything in one pass |
| Large or busy | `<Nullable>warnings</Nullable>` first (warnings without annotation semantics), fix those, then `enable` and fix the second wave |
| Very large legacy | Leave the project setting off; add `#nullable enable` per file as each is migrated |

Work from the center out: shared models, DTOs and utilities first, then services, then controllers and UI; in a solution, dependencies before consumers. Within a file, public and protected members first.

Build clean (`dotnet build --no-incremental`) at every checkpoint: incremental builds hide warnings in untouched files. Record the starting warning count.

## Warning-by-warning fixes

For each warning: is null valid here by design? Yes: add `?` upstream. No, and provably never null where the compiler can't see it: `!` with a comment. Not sure: it's nullable, or ask.

| Warning | Fix |
| --- | --- |
| CS8602 dereference of possibly null | Make the source `T?` if null is valid, else `!` with a reason. Not `?.`, which changes behavior |
| CS8600 / CS8601 possible null to non-nullable | Add `?` to the target, or `!` if provably non-null |
| CS8603 possible null return | The method can return null, so the return type is `T?`. This is the most important rule |
| CS8604 possible null argument | Make the parameter nullable if null is valid, or `!` if provably non-null |
| CS8618 non-nullable member uninitialized | Initialize it, make it `?`, mark it `required`, or `= null!` for members set after construction (framework lifecycle, builder) plus `[MemberNotNull]` on the initializing method |
| CS8625 null literal to non-nullable | Make the target nullable or pass a real value |

Helpful patterns:

- `Debug.Assert(x is not null)` informs flow analysis (stripped in Release, so it doesn't guard at runtime).
- One `= null!` on a late-initialized field beats fifty `field!` uses.
- `Where(x => x != null)` doesn't narrow `T?` to `T`; use `OfType<T>()`.
- Guard libraries whose parameters carry `[NotNull]` already narrow; don't add `!` after them.
- On an unconstrained generic, `T?` changes value-type signatures; use `[return: MaybeNull] T` or `[MaybeNullWhen(false)] out T`.
- `var` takes the nullability of the expression; declare the type when the declared nullability matters.
- APIs from libraries without nullable annotations are "oblivious": no warnings, no safety. Treat lookup-style returns as nullable.
- Generated files with an `<auto-generated>` header are excluded from nullable analysis.
- `?.` followed by `!` (`obj?.Prop!`) contradicts itself; pick one.

## Annotating declarations

- Nullable return: `*OrDefault`, `Find`, lookups that may miss, `ExecuteScalar` (`object?`, may also be `DBNull.Value`), anything documented to return null on failure.
- A parameter whose method handles null without throwing is `T?` (as `Path.GetPathRoot(string?)`); one where null throws is `T`. In gray areas prefer nullable; it can be tightened later.
- DTOs and serialization models cross trust boundaries: nullable by default, or enforced with `required`, `[JsonRequired]` or validation. Domain models enforce invariants in constructors and stay non-nullable.
- Struct reference fields are null in `default(T)`; nullable if `default` is valid usage.
- A member that becomes null only after `Dispose` stays non-nullable.
- An override may return a stricter `T` where the base returns `T?`; parameter nullability must match.
- Widely overridden virtual returns: `T?` if overrides commonly return null (`ToString()`), `T` if almost never (`Exception.Message`).
- `IEquatable<T?>`, `IComparable<T?>` on reference types; `[NotNullWhen(true)]` on `Equals(object? obj)`.
- Events: `EventHandler? handler = MyEvent; handler?.Invoke(this, e);`.

Libraries: annotations are source-breaking for consumers with nullable enabled (and `TreatWarningsAsErrors`). Record every public change (return `T` to `T?`, parameter `T?` to `T`, any value-type `?`) for the release notes, and ship in a minor version, not a patch. Enabling nullable makes every unannotated public reference parameter non-nullable implicitly; scan for ones that actually accept null.

## Attributes

`System.Diagnostics.CodeAnalysis`; for `netstandard2.0` or .NET Framework targets, use a polyfill (the `Nullable` package or internal copies).

| Attribute | Use |
| --- | --- |
| `[NotNullWhen(true)]` | `bool TryGet(..., [NotNullWhen(true)] out Foo? value)` with a non-generic out; `IsNullOrEmpty`-style checks; `Equals(object?)` |
| `[MaybeNullWhen(false)]` | Generic out parameters: `bool TryGet([MaybeNullWhen(false)] out T value)` |
| `[NotNull]` | A nullable argument is non-null after the method returns (`ThrowIfNull` helpers) |
| `[MaybeNull]` | A non-nullable generic return or field may be `default` |
| `[AllowNull]` / `[DisallowNull]` | Setter accepts null and falls back / nullable property must not be set to null |
| `[MemberNotNull(nameof(_x))]` | Helper guarantees fields are set; use one attribute per member (the `params` form isn't CLS-compliant) |
| `[NotNullIfNotNull(nameof(input))]` | Return is non-null when that argument is |
| `[DoesNotReturn]` | Method always throws |

The compiler doesn't warn about a misplaced attribute (`[DisallowNull]` on a non-nullable parameter, `[MaybeNull]` on a by-value input); check each one has an effect.

## EF Core and ASP.NET Core effects

Nullable annotations are read at runtime by these frameworks, so enabling them changes behavior, not just warnings.

- EF Core infers `string` as NOT NULL and `string?` as NULL. After enabling, generate a migration and inspect it for `AlterColumn` nullability changes before applying; existing null data makes those fail or lose data. Consider migrating entity classes one at a time.
- EF navigations: required reference navigation `= null!`, or `T?` when code checks whether it loaded; collection navigations non-nullable and initialized (`= []`). `DbSet<T>` properties stay non-nullable (EF Core 7+ suppresses CS8618 for them). `.Where(o => o.OptionalNav!.Prop == x)` in LINQ-to-SQL is fine; the database handles null.
- A private parameterless EF constructor: wrap it in `#pragma warning disable CS8618` / `restore`, always with the `restore`.
- MVC treats non-nullable reference properties as `[Required]`, so requests that sent null now get 400. `SuppressImplicitRequiredAttributeForNonNullableReferenceTypes = true` in `AddControllers` during a gradual migration.
- Minimal API parameters become required when non-nullable; use `string? name` to keep them optional.
- On .NET 9+, set `JsonSerializerOptions.RespectNullableAnnotations = true` (and `RespectRequiredConstructorParameters`) so System.Text.Json rejects null for non-nullable properties. It can't see collection element, dictionary value, generic argument or top-level nullability.
- Razor Pages `[BindProperty]` models: `= default!`.
- For files not yet migrated, use `#nullable disable`, not `#nullable disable warnings`: the latter keeps annotations active, and EF and MVC still read them.

## Validate

1. Clean build with zero CS86xx warnings.
2. Lock it in: `<WarningsAsErrors>$(WarningsAsErrors);nullable</WarningsAsErrors>`.
3. Tests pass.
4. Review the diff: only `?`, `!`, attributes and directives; no new `?.`, no removed null checks, no new branches. Each remaining `!` and `#nullable disable` has a reason. Public signatures match intent, including unchanged members that became implicitly non-nullable.
