# Agent briefs

An agent brief is a comment posted when an item reaches `ready-for-agent`. It is the contract an unattended agent works from. The original body and discussion are background.

The item may wait for days, and the code changes meanwhile, so write for durability:

- Describe interfaces, types, and behavior. Name the types, function signatures, or config shapes to look for.
- Leave out file paths and line numbers, and don't assume the current structure survives.
- State behavior, not procedure. "`SkillConfig` accepts an optional `schedule` of type `CronExpression`" beats "add a field on line 42 of types.ts", because the agent explores the code fresh and chooses its own implementation.
- Give acceptance criteria that can each be verified alone. "Triage works" fails. "`gh issue list --label needs-triage` shows only items that finished initial classification" passes.
- State what is out of scope, so the agent doesn't widen the change.

For a PR, "current behavior" describes the state of the diff, and the brief says what remains: finish it, close gaps, address review points. It never restarts from scratch.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent brief

**Category:** bug / enhancement
**Summary:** one line on what must happen

**Current behavior:**
What happens now. For a bug, the broken behavior. For an enhancement, the status quo it builds on.

**Desired behavior:**
What should happen when the work is done, including edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what changes and why
- `functionName()`: what it returns now and what it should return

**Acceptance criteria:**
- [ ] Specific, testable criterion
- [ ] Specific, testable criterion

**Out of scope:**
- Adjacent behavior that stays as it is
```

A `ready-for-human` note uses the same structure and adds a line on why a person is needed (a judgment call, external access, a design decision, or manual testing).
